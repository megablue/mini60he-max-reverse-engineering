AGENTS.md

Before you grep, glob or open a source file: read HANDOFF.md, then docs/features/index.html, then only the feature page(s) for the area you are about to change. The feature pages name the files, functions and tests you would otherwise hunt for — the code comes after them, not before.

Mini60HE Max Firmware Reverse Engineering is a reverse-engineering workspace for the Mini60 HE Max keyboard's Windows companion software: one stock binary is held as immutable evidence, and every deliverable is recovered knowledge — what the app does, what its settings control, and how it drives the keyboard.

Three kinds of document, and keeping them apart is the point:

  • docs/SPEC.md is product behavior — what the product does and what a user sees, readable without knowing the code. Behavior belongs there even when the code is where the reason for it lives.
  • docs/features/ is the feature map — one page per feature with its files, mechanisms, traps and pinning tests. Read the page for the area you are about to change; keep it true in the same commit.
  • This file is process and hard rules — the commands, the workflow and the constraints that apply across every feature.

Where a rule has a behavior half and a mechanism half, the behavior half is a pointer to docs/SPEC.md and the mechanism half to its feature page rather than a second copy: two copies of a default value is one more thing that can be wrong.

AGENTS.md and docs/SPEC.md are HTML documents (AGENTS.html, docs/SPEC.html); the .md files beside them are pointer stubs that only keep the paths alive, so edit the .html directly.

Read first

HANDOFF.md holds the current state; if it is missing, carry on with the feature map and the code. Then docs/features/index.html — the feature map — and only the feature doc(s) for what you are about to change. docs/SPEC.md is user-visible behavior; this file is process and hard rules; the feature docs are the map, the mechanism and the traps.

Layout

  • bin/ — stock evidence. The vendor binary (MINI 60 HE MAX_V1.52.exe, SHA-256 pinned below), copied in verbatim. Why it is separate: everything else in this workspace is derived work; this directory is the ground truth every claim is checked against, so it is never edited, only re-hashed.
  • docs/ — SPEC.md (behavior) + features/ (the map). Created by this scaffold; pages are added as RE areas emerge.
  • analysis/ — static-probe tooling and its reproducible artifacts. probe_pe.py parses the pinned exe as data (hash, metadata, imports, resource tree, strings) and never runs it; probe_cert.py walks the Authenticode overlay with a minimal DER reader into certificates, signer chain and RFC 3161 timestamp. out/ is what they wrote, with census.txt as the summary. Re-running the script regenerates out/. The firmware probes work the same way on the extracted image: fw_code.py (recursive-descent map), fw_keys.py (key/layer tables), fw_feat.py (layout/LED band), fw_sensor.py (scan front end, with asserts), probe_radio.py (negative evidence for a radio or companion chip) and fw_fn.py/fw_find.py (annotated disassembly lookups). Phase 5 added two more: fw_patch.py (the modification surface — every patch target byte-exact, out/fw_patch.txt) and isp_gate.py (chip-record table and the RCDATA size gate, out/isp_gate.txt). fw_remap.py is the remap planner: it resolves a requested key mapping, validates it and prints the byte edits (out/fw_remap.txt), never writing an image. fw_build.py is the one-command builder: requests in ("CapsLock=Esc"), a patched image and a wrapped updater out, with the finished diff asserted against its own edit set; fw_names.py holds the usage vocabulary both of them share. fw_bake3.py and fw_volpatch.py are the earlier hand-written bakes and stay as the record of what was flashed. fw_deadwin.py is the first build that adds code rather than data: a four-byte hook at the report funnel 0x127E0 plus a 64-byte stub in blank flash that drops keys for two seconds after a wireless wake (out/fw_deadwin*, out/fw_deadwin_remap*).
  • Analysis artifacts (disassemblies, unpacked payloads, scratch tooling, reports) get top-level directories when created, each with a bullet here in the commit that creates it. Do not scatter artifacts under a feature page.

Nothing is built, tested or linted yet — the workspace is evidence plus docs. The gate before a commit is evidentiary, not automated:

to an artifact or a command in the workspace → feature page updated in

When tooling exists, its gates get added here in the same commit as the tool. Useful today:

# pin / verify the evidence binary (PowerShell, from the workspace root)
(Get-FileHash -LiteralPath 'bin\MINI 60 HE MAX_V1.52.exe' -Algorithm SHA256).Hash

Workflow

  • The features map is part of the change, not the cleanup. Before staging a commit, update the feature doc(s) for whatever you changed (docs/features/), and add an index row if the doc is new. User-visible behavior also updates docs/SPEC.md in the same commit. A docs-only follow-up commit is the one that gets skipped. Pure refactors with no behavior, mechanism, config or test change need no doc edit — do not churn the map.
  • Read the map before the code, and keep the map worth reading. A feature page is an anti-hunting payload: the file, type, function and test names for one area, and the traps that cost someone an afternoon. Opening the source first and writing the page afterwards spends the tokens twice. If a page is wrong, fix it in the same commit rather than working around it — a map nobody trusts is worse than no map.
  • Search the map in the same breath as the code. A grep for a feature, a symbol or a behaviour runs over docs/features/ too: the feature pages name the identifiers and the tests, so the page you need is usually one hop from the hit.
  • HANDOFF.md is refreshed at the end of a session, not per commit. It carries what only the passing session knows — open threads, next steps, the last thing delivered — under an As of stamp. It is allowed to lag the tip: its header says the code wins. Refresh it before you hand the work over.
  • Measure, don't deduce it. Reading the code and doing the arithmetic in your head is how geometry, layout and formatting bugs ship. Print the real numbers from the real thing — a headless run, a scratch script, the actual command — and assert both the good and the broken case, so each test carries its own failure mode.
  • Gate on the whole check set, not just the tests. The linter catches the classes of defect the test run compiles straight past. Run the formatting, the lint with warnings denied, the tests and the build before you call something done.
  • Commit messages go through a file. Write the message to a scratch file (this machine uses %LOCALAPPDATA%\Temp\opencode\<project>-commit-msg.txt) and run git commit -F <path>; a PowerShell here-string gets its terminator mangled by the shell tool.
  • No AI attribution in a commit message, ever, without being asked. No Co-Authored-By trailer, no Generated with footer, nothing that reads as crediting a model or tool. These commits are the user's. This is enforced, not merely preferred: a machine-wide commit-msg hook (core.hooksPath pointing at the user's global hooks directory) rejects the commit outright, and it blocks human co-authors too, so the only ways past it are --no-verify or ALLOW_COAUTHOR=1. Use neither without the user asking in that conversation. If the hook blocks something, report it and stop; do not reword the message to slip a trailer past the pattern.
  • Package after committing. If the version is derived from the commit (a count since a base tag, a stamped build number), packaging first yields the previous commit's number. Raise the minor and the base together, in the same commit, and keep every reader of that number reading it from one place.
  • Do not commit before the user has looked at it. Hand a visual change over as a build and wait for confirmation.

Where the working knowledge lives

The per-feature working knowledge lives in docs/features/; its index.html is the index. This file keeps the process rules and the hard rules that apply across features; the feature pages keep the maps, mechanisms and traps.

Feature pages are HTML documents. A code-shaped block is pseudocode — <pre class="pseudo"> — because an agent copies the shape, not the bytes; <pre class="verbatim" data-why="…"> is only for a block whose exact bytes matter, and the reason is mandatory. A graph is <pre class="mermaid">; the tool hands the agent an edge list and the browser draws the picture. A map written as Markdown is still read, and feature_map_upgrade converts one.

Hard rules

  • bin/ is immutable. Never edit, rename or re-encode anything in it. The pinned SHA-256 lives on the evidence feature page; re-hash before publishing any claim traced to the binary, so a swapped file cannot silently invalidate the documentation.
  • The file name lies about the version. …V1.52.exe reports PE version 2.1.2.13 internally, and its version strings are otherwise empty. Every reference to the binary cites the SHA-256 (prefix OK or full hash), never the file name alone.
  • Behavior claims carry evidence. docs/SPEC.md states only observed, reproducible behavior; speculation is welcome in docs/features/ pages but must be tagged speculative there and must never reach the spec until verified.
  • No repo yet. Commit-rules above stay dormant until git init; when initialized, this scaffold is the first commit. Hand a visual change over as a build and wait for confirmation.
  • The README is for users. Implementation detail belongs in docs/SPEC.md for behavior and here for working knowledge, and the user must be consulted before technical detail is added to the README.
