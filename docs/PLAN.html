Plan

This page is how this project moves forward: the goal, the fences nobody crosses, the six phases, and where the work actually stands. Findings live in the feature pages, process and hard rules in AGENTS.md, verified behavior in docs/SPEC.md, session state in HANDOFF.md — this page only decides what happens next.

Goal

Reverse engineer the Mini60 HE Max updater executable — a SONiX USB MCU ISP Tool (bin/MINI 60 HE MAX_V1.52.exe, hash-pinned on Binary evidence) — and the keyboard firmware image embedded inside it, so keyboard functionality can be modified later. Per the user (2026-10-22), explore and decode first; afterward all three modification areas are on the table: key remapping, lighting/RGB, and performance (debounce/polling).

The analysis is read-only for as long as the keyboard is this machine's daily driver, and the updater is never a program we run — it is data we parse.

Fences

Every phase runs inside these. A task that cannot be done inside them waits.

  1. Never execute the updater. No run of bin/*.exe, no installer, no drive-by invocation; static parsing only (Python via stdin here-strings, PE/zip resource parsing).
  2. No device contact while the keyboard is the daily driver. The HID surface is studied statically - feature-report IDs read out of the disassembly; nothing enumerates, opens or talks to the HID interface. This binds the analysis, not the owner: the one write so far (2026-10-22) was performed by the owner with the vendor tool, and no script in this repository opened the device.
  3. The binary stays immutable and hash-pinned. Every claim traced to the exe cites the SHA-256 pin, re-derived before publishing (AGENTS.md hard rules; the Binary evidence page owns the pin).
  4. Phases 1–5 write no firmware anywhere. Building a patched image and any flashing is phase 6, explicitly user-gated. The updater has no flash-read command (see ISP protocol), so the pre-flash backup is the factory image RCDATA 4000 kept outside the keyboard — not a device dump — and equality with the device cannot be proven with this tool.

The first patch: Fn + Right Arrow = Volume Up

The first candidate, and the image that was actually written on 2026-10-22. It needs no code, no relocation and no added length: four bytes — two inside the Fn map in a row no physical key can reach, and two in the usage table, where the role swap was assumed to live. The flash split that assumption: the Fn-map pair is live, the usage-table pair is inert. The durable bake puts the same two roles in the key catalog, where the output is read.

ItemValue

Why rows 3/4Fn-held is keyed on the usage value 0xAF, not on an id: the key at the old RAlt position already produces Fn+1 = F1 on this keyboard only because an app remap put 0xAF on it. The intent was to bake the swap here so the image is self-contained — an ISP reflash otherwise wipes the NVM pages the remap lives in. The flash showed this table does not drive output, so the durable version of these two edits sits in the catalog (0x9752/0x9756) and this table is kept in step for the reverse lookup.
Why row 32Of 51 rows, only rows 1–12 (F1..F12; a 60% has no F-row) and row 32 (0x4C Insert; no such key) are unreachable. Repurposing row 32 costs nothing.
Why 0xB9The Fn output byte is a vendor enum, not a HID usage: 0x16BF6 is indexed as 0xB0 + k into consumer usages. 0xB9 → 0x00E9 Volume Up. Four members confirmed on the keyboard (0xB0 next, 0xB1 prev, 0xB3 play/pause, 0xB5 mute).
InvariantsLength unchanged (size gate cannot trip), row count stays 51, every byte below 0x16A96 identical (version words), no other id carrying 0xE6/0xAF/0x4F left behind (asserted), no id gains or loses its scan position (per-key actuation records stay put).

Test ladder

  1. Zero risk, on stock firmware: Fn+F12. The factory image already maps it to 0xB9, so a volume change proves the enum and the Fn input path on hardware before anything is written. Done 2026-10-22: it raised the volume.
  2. Artifact (built): analysis/fw_volpatch.py → out/fw_volplus.bin and out/fw_volpatch.txt; it asserts every invariant above, including that no other id carries the swapped usages. Result: exactly four bytes differ, length unchanged, sha256 ac46b5aa…. --chord-only builds the two-byte variant for use only while the app remap is guaranteed to stay. It never touches bin/.
  3. Gated flash, then Fn+Right = Volume Up while every stock Fn combo still behaves — and the old RAlt position is now Fn, the old Fn position now Right Arrow. Executed 2026-10-22: the chord worked once the app remap was re-applied; the role swap did not happen. See below.

What the first write proved (2026-10-22)

The owner flashed analysis/out/MINI60HE_max_bake.exe — the vendor installer with only RCDATA 4000 replaced by fw_volplus.bin — through the tool's own Start button. No script in this repository ran the updater. The board booted, typed normally and the version gate accepted the image. Measured results:

  • The write path works end to end. A same-length image loaded through the dialog reached flash and the keyboard came back on it; no tool guard tripped.
  • The NVM pages are wiped. The owner's app-side macro and CapsLock remap vanished and had to be re-entered — 0xB000/0xB600 sit inside the written span, as predicted.
  • The usage table is not the output path. Both 0x16E83/0x16E85 edits changed nothing: the old Fn key still acted as Fn and old RAlt stayed right Alt. Key output is read from the per-key catalog at 0x9600 + id*4 (usage in byte 2); 0x16DD8 only feeds the usage→id reverse lookup at 0x327C.
  • The Fn row is live. After re-applying id 0x54 → 0xAF and id 0x55 → 0x4F in the app, Fn + old Fn key produced Volume Up — row 32 (0x16C7E/0x16C7F) works on hardware. Fn+1 = F1, Fn+W = BT host 2 and Fn+F7–F10 = prev / play-pause / next / mute had already fixed the enum.

What the catalog bake costs

bake3 moves the swap to where the output is read: 0x9752 E6→AF (id 0x54) and 0x9756 AF→4F (id 0x55) in the catalog, the same pair in 0x16DD8 to keep the reverse lookup consistent, and the row-32 Fn edit. It also parks Up/Left/Down on right Shift, Menu and right Ctrl (0x972E E5→52, 0x975A 65→50, 0x975E E4→51). Cost: Right Alt and the factory Fn position disappear as such, and those three keys stop being themselves. No scan-grid edit, so ids keep their positions and per-key actuation records stay put. The factory RCDATA remains the revert. bake3 is built (analysis/out/MINI60HE_max_bake3.exe, sha256 774bb728…fe9a9) and has not been flashed.

Before the next write

  • The app's remaps and the owner's macro live in the NVM pages 0xB000/0xB600, inside the span the ISP tool writes, so a flash erases them — measured on 2026-10-22. The catalog bake does not need the app's right-arrow remap, but the macro and any other remap have to be re-applied after the flash.
  • Open: whether the companion app rewrites the keymap when it connects. If it pushes its own settings over the catalog defaults, the catalog bake's roles would be overwritten after the first app connection. This is the cheapest thing to watch on the spare unit.
  • Rollback is the factory image itself: RCDATA 4000, SHA-256 06a1a474…a88e0, kept in the exe and in analysis/out/fw_stock.bin.

Gates

The second-unit rule applies to the next write: an unmodified image first, proving the write path with zero behavior change, and the daily driver is never the first device. The 2026-10-22 write took the daily driver straight to a modified image, so it bought the path proof at the cost of the settings and without a recovery story. Recovery from an interrupted write is still not demonstrated, which is why the spare unit goes first.

Flash runbook (next write)

One write has already happened: the owner flashed the four-byte image on the daily driver on 2026-10-22 (results above). Because that skipped the safety order, this runbook is the stricter rule for the next write, which is the catalog bake. Both artifacts are 0x7E000 raw binaries plus the wrapper exe the tool accepts through its open file dialog:

  • Factory: analysis/out/fw_stock.bin — copy of RCDATA 4000, SHA-256 06a1a474…a88e0. Flash this first on the spare unit.
  • Bake: analysis/out/MINI60HE_max_bake3.exe, or fw_bake3.bin loaded into the stock exe through the tool's dialog — image SHA-256 617eef7f…c744cd16, exe SHA-256 774bb728…fe9a9. Flash this second, only after the factory run behaves.

Container: .bin is supported, not a fallback

The dialog filter is *.hex,*.bin. The handler at 0x423B90 matches L".hex" then L".bin" against the chosen path and stores 1 or 2 at dialog +0x428; the .bin branch memsets the 1 MiB firmware buffer (fill 0xFF for this chip family) and reads the file into the same pointer the bundled-RCDATA loader uses, [dialog+0x1E44] — the pointer the upload flow at 0x401100 reads. So a raw .bin reaches the writer; no Intel-HEX wrapper is needed.

Order

  1. Spare unit only, on a wired connection, tool not otherwise touching the daily driver.
  2. Flash fw_stock.bin. Note the version and checksum strings the tool reports.
  3. Verify stock behaviour: typing, CapsLock toggle, Fn+F12 = volume up, Fn+S/Fn+D/Fn+A = Windows/Mac/Android, and that the app's settings pages read back blank after the write (the 2026-10-22 flash emptied them).
  4. Flash the bake3 image. Same checks, then Fn+Right = volume up, old Fn key = Right Arrow, old RAlt position = Fn, and right Shift/Menu/right Ctrl = Up/Left/Down.
  5. Re-create the owner's app-side macro/remap afterwards: the NVM pages are inside the written span, and the 2026-10-22 write emptied them.

Stop if

  • The tool reports a version or checksum that differs from the stock run — the loaded file is not what it should be.
  • The tool reports Firmware Version is not for this chip!! — that is the version gate refusing; do not force anything.
  • The device drops off mid-write. Do not retry blindly: no recovery path is demonstrated and no read command exists to inspect the device state.

Still inference, not capture

  • Write span: the loop bound comes from the same flow that writes the bundled image, so the 1 MiB buffer's 0xFF tail should never be written — reasoned, not traced to the loop counter.
  • Recovery from an interrupted write: bootloader lives outside 0x7E000, entry unproven.
  • The .hex branch (type 1) is untested for this image; neither artifact needs it.

Candidate modifications, ranked by cost

Nothing here is committed work; it is the menu the analysis has earned. Every entry is table data or tooling, not new firmware code, because the two levers are already proven on hardware: the key catalog at 0x9600 + id*4 (4-byte record, kind 2 with the usage at +2) decides what a key sends, and the Fn overlay at 0x16C3E + row*2 (51 rows, input usage → output enum) decides what Fn+key becomes. The output column is not HID: it is a vendor enum resolved through 0x16BF6 (media, 0xB0–0xC0) and 0x16BE6 (WASD/arrow virtual codes 0xF8–0xFF).

Tier C — small code constants (in place, 2–4 bytes)

Snappier key feel: hysteresis 0x0C at 0x3764, commit delta 0x0A at 0x54DE, hold timer 0x1388 at 0x54A6. This is the only genuine performance knob found, and also the easiest way to introduce chatter, so it needs a tuning ladder rather than a single write. Second Fn is already specced but is not small: it is the first patch that must add code (~60–120 bytes into blank flash, 2–4 days, 2–3 flashes) — see A second Fn key (Fn2).

Ruled out, and why

  • Wireless dead window. The unresponsive seconds after a wireless wake cannot be in this image: a wired replug resets the MCU and is instant, so boot plus Hall calibration are sub-second; the delay is RF link establishment in the dongle/module, outside 0x7E000.
  • Macro engine. The per-key model is one 4-byte record — a single usage or a single special action. A multi-step timed macro has no storage slot, so it is a code and data-format project, not a table edit.
  • Flash readback. The updater has no read command at all, so a stock backup, a diff after writing, or a settings export all stay impossible. Every write remains one-way.

The rule that keeps these cheap

All of Tier A and B preserve the image length and touch only tables at 0x9600 or above, so the tool's size gate and checksum behave exactly as in the stock flow. The one gate that could still refuse a write is the version word, compared against a dword read at fwbuf[idx*2] for a small idx taken from the chip record — no table at these offsets can be that word. A refusal is a pre-write check, so a mismatch costs a click, not a keyboard.

Strategy: patch, not rebuild

Asked whether the firmware could be rebuilt from source, the answer is no, and the record lives in Rebuild or patch: 36.1% of main code reached with 177 orphan runs, no SoC register documentation, no debug or readback path, an unknown device-side bootloader, an unexamined runtime config protocol, and a wireless module whose firmware is not in this image. A byte-exact rebuild is unattainable in principle; a behavioural rewrite would be a new wired keyboard.

What the evidence supports is a patch spectrum — table or constant, in-place code, and hooks into the roughly 400 KiB of blank flash above 0x18600 — under one rule: table edits come first, a hook is spent only on a feature with no table slot, and every write is one falsifiable hypothesis, validated on hardware before the next layer is trusted. The constraints (no readback, settings wiped on every flash, interrupted-write risk, wireless out of reach) are on that page rather than repeated here.

  • Target locked (2026-10-24): the Fn output column is a vendor enum (0x16BF6, indexed 0xB0 + k). Five on-keyboard tests fixed it: Fn+1 = F1, Fn+W = BT host 2, Fn+F7/F8/F9/F10 = prev / play-pause / next / mute. 0xB9 = Volume Up, 0xBA = Volume Down — and rows 11/12 already map F11/F12 to them, so Fn+F12 is a zero-flash proof of the whole chain.
