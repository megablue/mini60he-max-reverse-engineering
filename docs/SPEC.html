Mini60HE Max Firmware Reverse Engineering — behavior spec

User-visible behavior only: what the product does and what a user sees, readable without knowing the code. Behavior belongs here even when the code is where the reason for it lives — the reason, the mechanism and the traps live in docs/features/, and process and hard rules live in AGENTS.md.

Each section below covers one user-visible area, in the order a user meets it.

Scope

What this product is: the Mini60 HE Max keyboard's Windows companion software (bin/MINI 60 HE MAX_V1.52.exe, 2,386,384 bytes, PE version 2.1.2.13, SHA-256 958A39951D2F908A7FE925E0FA598C321924CB235239BF37484AE7C8213512D6), as observed by reverse engineering. "User" here means whoever runs this software on their keyboard; sections appear as RE pins them.

What this project deliberately does not do: it does not reimplement the app, does not rehost the binary's code as source, and it never guesses — a section exists here only once something was observed and verified.

Identity

Everything below is read out of the pinned binary and the firmware image it carries; none of it has been observed on hardware yet, so these are the firmware's claims about itself, not bench measurements.

  • The keyboard is driven as a HID keyboard, and the updater identifies its board by vendor 0x0C45 / product 0x80A1. The firmware carries the product string MINI60HE MAX.
  • The controller is a SONiX SN34F280 on the 108A board. The updater also knows other SN8F/SN32F boards, which is why its chip list names parts this keyboard does not use.

Typing

  • 61 physical keys are scanned continuously. Each key resolves to one logical key id, and each id resolves to one HID keyboard usage.
  • Fn behaviour depends on an OS mode selected with Fn+S (Windows), Fn+D (Mac) or Fn+A (Android), stored as a mode byte and applied to the Fn overlay. The Windows overlay is the full Fn map: number row → F1–F10, -/= → F11/F12, K/L/U/I/O → Home/End/PrintScreen/ScrollLock/Pause, Delete → Insert, ;/' → PgUp/PgDn, / → Insert. The Mac and Android overlays pass F1–F12 and Fn through unchanged and otherwise match it; the fourth table copy has no selector and is unreachable. Without Fn, every mode types what is printed on the key.
  • Most keys produce a standard keyboard usage. A set of extended action codes (media, lock keys and similar) is consumed by the report builder instead of becoming a usage, so those keys cannot be described as plain usages.

Actuation and debounce

  • Each key has a press threshold of 2400 and a release threshold of 1600 in raw 16-bit sensor units, with a 12-unit hysteresis band: a key must travel back up past the release threshold before it is allowed to release.
  • State changes are filtered. A raw jump of 10 units or more commits immediately; smaller movement waits out a 5000-cycle stability countdown. That filter is the anti-chatter/debounce path and the place a performance change would land.
  • The cycle count is not yet tied to a wall-clock time base, so 5000 is a number of filter calls, not a verified number of milliseconds.

Lighting

  • Keys are grouped into 14 lighting groups (ids 0x00–0x0D) that cover 58 of the 61 key ids; a group lights its members together.
  • The engine ships waveform lookup tables (breathing and sine-shaped ramps that mirror back down), a primary palette (ff0000, ff8000, ffff00), per-profile hue values, and effect-speed presets of 200/150/100/75.
  • The LED driver is initialised by register writes to a peripheral block at 0x4001B2xx. All of this is table data in the image, not code, so a lighting change is a table edit.

Settings

These are the values the companion app holds for the connected board; the app seeds them from data inside its own executable, which is why they are describable without ever running it.

Key mapping, actuation and lighting are deliberately absent: those values exist only in the firmware image, with no decoded companion-app control, so they appear as observed behavior above and as tables in the feature pages.

Updating the keyboard

  • The updater talks to the keyboard over HID feature reports only — no mass-storage or serial path.
  • Before writing, it compares the version word in the firmware file with the version bytes the device reports and refuses to continue on a mismatch (Firmware Version is not for this chip!!).
  • It displays a 16-bit checksum of the loaded file; the hex-file and bin-file paths have separate checksum displays, and the firmware image carries no checksum field of its own.
  • It has no command that reads back flash contents. It can program, erase and verify, but it cannot dump a stock image, so a backup has to be the factory image extracted from the updater itself — and the updater cannot prove the keyboard matches that copy.
  • Flashing is gated in this project (phase 6, user-approved only): nothing described here has been written to a device.
