The wireless dead window — drop the first 2 s of keys after a wake

Status: solved on hardware (2026-10-25) and shipped (2026-10-26) — the wake leak was a factory-value fallback supplied by the settings filler, and deleting it removed the wrong key; the remaining limitation, that the first press after a wireless wake is silent instead of running its macro, is accepted and documented at the first press · Read when: the first press after a wireless wake carries the wrong (factory) binding, asking why that first press does nothing, planning a wireless-only gate, or asking where a key report can be dropped before it reaches the host

What it is

The report from hardware, in three rounds:

  • Wireless only. Wired replug and a wired mode switch are immediate. In 2.4G and in Bluetooth there is a window of about 2 s after a wake from idle.
  • It is not a dead window. A press inside it does reach the host, with the key's factory binding. The macro key sends CapsLock (its factory usage), so one press leaves the host's caps state toggled.
  • After the window the configured macro works. The same key never sends CapsLock again until the next wake.

The request: make the window real — throw the presses away instead of sending the wrong thing, for about 2 s, and only while the keyboard is wireless.

2026-10-24, after the first write: the built patch was flashed (out/fw_deadwin_remap.exe, 7dd6a392… — the arrow bake plus this stub). The keyboard boots and types, the arrow cluster still works, and a wireless wake still leaks CapsLock. Two presses during the window still reach the host. The wake itself is instant; the window is still about 2 s. So the drop did not take effect, and the next step is not another guess but a build that reports what the stub sees — see the marker build.

Why the wrong binding appears

The key handler stages a binding in two steps, and both are in the image:

  • Factory first. 0x5A00 looks the scan position up in 0x16B3E (position → factory usage) and writes that usage to the output slot 0x2000008C at 0x5A22, before it applies the per-key record. For the macro key that byte is 0x39, CapsLock.
  • Configured second. The per-key record lives in RAM (0x200024AE catalog, 0x200028AE settings). Wirelessly it is filled by the RF settings channel: 0x10058 handles module frames 0x23 and writes flash tables 0x9000/0x9600/0xB000/0xB600 plus their RAM mirrors.

2026-10-24, user tests: the configuration is not held by the dongle. Unplugging and replugging the receiver does not bring the factory binding back, and the settings survive a keyboard power cycle — they are in the MCU's own flash. So the window is not "the config was lost"; it is "the table in RAM is not the user's one yet when the first press arrives".

The static side of that: the per-key tables are rebuilt by 0x59F0, and that function has exactly two callers — 0x6BE6 and 0x6F16. The second sits inside the link-up re-init 0x6EB8, which 0x1834 runs once it decides the module is ready. So the rebuild is part of the link-up path, not of the boot path, and the presses that arrive before it runs read whatever the tables held at that moment.

So a press that lands before the channel has delivered the user's records takes the factory path — and the firmware's own link indicator agrees: the module handshake declares the link ready by writing lighting state 0x4B at 0x1EB2, and only then does the configured effect return.

That also disposes of the earlier "it is a hardware CapsLock flag" idea: the image has no caps flag at all, CapsLock is just usage 0x39 in the catalog record of id 0x30.

Where a press can be dropped

0x127E0 is the single action-byte → HID converter: it is where a usage is written into the report buffers (modifier byte 0x200000DE, consumer slot, 128-bit bitmap 0x20002144) and where the "report changed" flags are set. Every emission passes it:

  • the final-usage dispatcher tail-branches to it at 0x147F8 (b.w 0x127E0) — the path a plain key takes;
  • the modifier/Fn kinds call it from 0x5A00 (0x5B82, 0x5B9C, 0x5BEA, 0x5C4A, 0x5C58).

The report is assembled later from those buffers: 0x15FC folds them and clears them, then hands off to the USB task at 0x10768. If nothing is staged, the fold sees nothing and the report carries no key. Returning early from the converter is therefore a clean drop, and the caller cannot tell the difference.

Its first instruction is a 4-byte push.w — one whole instruction — so the entry can be replaced by a 4-byte branch with nothing left over, and the stub can replay the push.

How a wake is detected

Wireless is free: the mode object at 0x20000378 holds 0 for wired and 1/2 for 2.4G/BT, written by the two-pin debouncer 0x107B8. No new detection is needed.

A wake edge is not free. The candidates all carry a re-arm risk:

CandidateWhy it was not chosen
mode debouncer 0x107B8, stable-change bankA genuine edge, but it fires on a wired↔wireless switch only — not on an idle wake, which is the reported symptom.
link-ready block 0x1EAE / lighting 0x4BInside the module reply handler. It may run on every reply; arming there could re-arm forever and mute the keyboard. Not provable statically.
link countdown 0x200003B0Only one static reader (0x1848) and no static writer — its edge cannot be trusted.

Chosen: our own idle edge. The stub keeps two dwords, last key and armed. In wireless mode, if the gap since the last key is at least 30 s, that press is the wake: arm the timer at "now" and drop the press. Suppress while "now − armed < 2000 ms". Wired mode does not touch the state at all, so switching from wired also arms on the first wireless press.

This is a heuristic, and it is honest about it: it cannot tell a wake from a 30 s pause. The cost of being wrong is one dropped key plus 2 s of dropped keys after a long pause; the cost of the alternative is a keyboard that can mute itself. It is also self-limiting — an expired timer cannot stay armed, and there is no latch to get stuck.

It also had a hole in it, found after the failure. The gap is measured against a remembered press time in RAM, and the clock is the SysTick millisecond counter — both of which are 0 right after a boot. If the wireless wake restarts the MCU, the very first press after the wake sees now - last = 0 - 0 = 0, so "at least 30 s idle" is false and the window is never armed. A reset is the one moment the heuristic cannot detect, which is why the boot-window build keys on uptime instead.

The patch

Two sites, 68 bytes total: the hook at 0x127E0 (replacing the stock push.w) and a 64-byte stub in the blank band at 0x20000. The stub is hand-assembled and asserted by disassembly in the builder.

State, time base and builds

State: two dwords at 0x20000610 (last key, armed). That address sits in a 0x1EC-byte hole between 0x2000060C and 0x200007F9: no literal anywhere in the image names it, and an effective-address scan of the whole code region finds no load or store in 0x20000600..0x20000800. The builder re-runs that scan over its window and refuses a candidate that is referenced.

Built and flashed (2026-10-24): on the stock image, out/fw_deadwin.bin 2a26756a… and out/fw_deadwin.exe 4cbf3097…; on top of the arrow-cluster bake, out/fw_deadwin_remap.bin 4dd3201c… and .exe 7dd6a392… — that last one is what ran on the device, and it did not produce a dead window. --window and --idle retune the two immediates; every other byte of the stub is asserted against the disassembly above.

Time base: the SysTick handler 0x3FE8 adds the step byte to 0x200004A8, and the reload at 0x4044 divides the core clock by 1000/step — so that counter is milliseconds by construction, whatever the step is.

What it costs

  • One flash. New code, so it needs a write; every write erases the NVM settings pages, so app-side remaps are re-entered afterwards.
  • A heuristic window. A 30 s pause followed by a key is treated as a wake: that key and the next 2 s are dropped. Both constants are two immediates in the stub (0x7530 and 0x7d0) and can be retuned without touching anything else.
  • No macro, no config, no radio work. It hides the wrong binding; it does not stop the replay, shorten it, or teach the keyboard to hold keys until the config is ready. That larger fix would need the config-ready signal this page could not pin.
  • Wired is untouched — byte for byte the same path, because the first branch leaves when the mode byte is 0.

Gates

  • Length preserved: the image stays 0x7E000; the tool's RCDATA size gate sees exactly what it saw in the stock flow.
  • Checksum: computed tool-side from the loaded file (0x40A7D0/0x40A800), so nothing to patch.
  • Version word: 0x127E0 was a valid function prologue and 0x20000 was zero fill, so neither can be the dword the gate compares with the device's version — and a mismatch is a refusal before erase, not a brick.
  • No readback: there is still no way to dump the device, so every test is a flash; keep the unmodified updater as the revert path.

Test ladder

  1. Wired first. Type, chord, macro: nothing may change. This proves the branch out and the replay of the push.
  2. Wireless, one key after 30 s idle. The first press must do nothing; the host must not see CapsLock.
  3. Wireless, type immediately after that. Keys inside the 2 s are dropped; the first key after 2 s works, with the configured macro.
  4. Wireless, continuous typing. Gaps under 30 s must never arm: no key may disappear mid-sentence.
  5. Wired→wireless switch after a pause. The first press is dropped (the last wireless press was more than 30 s ago), then normal.

Run on 2026-10-24: failed at step 2. The press reached the host with the factory binding, and the arrow cluster and wired behaviour were unchanged. That is why the marker build exists.

Marker run, same day: worse. With the marker build flashed, lighting still reacted per press but the host received no keystrokes at all — writing the action byte at the funnel entry breaks the staged pipeline itself, not just the emitted key. The keyboard was recovered by reflashing the drop build (7dd6a392…), which types normally. That recovery is itself evidence: the hook and the stub prologue execute, so the drop branch simply never matched.

The marker build

There is no readback, so the device has to report the value itself. analysis/fw_deadwin_probe.py keeps the hook, keeps the timer, and throws the drop away: instead of returning early it writes one letter into the action byte 0x2000008C, a few instructions before the stock converter reads it. Whatever the host types is the stub's answer.

LetterThe stub saw
amode byte 0x20000378 is 0 — "wired"
qwireless, and the elapsed time is inside the 2000 ms window
wwireless, and the window has expired

Reading it:

  • Still CapsLock, no letters at all → the hook or the write never landed, and the leak is upstream of this funnel.
  • a at every press → the mode byte reads 0 in wireless; the predicate has to come from something else.
  • a inside the window, w after it → the switch read lies during bring-up and only settles later.
  • q for ~2 s, then w → hook, mode and timer are all correct, and the early return is what loses the drop; suppress later, where the report is built.

It writes the same two sites (hook at 0x127E0, 88 bytes at 0x20000) and touches nothing else, so the gates below apply unchanged. It drops nothing, so the keyboard types letters until it is reflashed — the vendor updater is the way back. A press may print its letter more than once (the release can pass the funnel too): read the letter, not the count.

Built and flashed (2026-10-24): out/fw_deadwin_probe.bin 21223c42… and out/fw_deadwin_probe.exe bf2c662d…, on top of the arrow-cluster bake. 81 image bytes differ (4 for the hook, 77 of the stub — the rest of the 88 was already zero) and 93 in the exe (the bake's 12 plus those). It silenced the keyboard completely: lighting kept reacting, the host got nothing. Reflashing the drop build restored typing, so the write and the branch both work and the whole marker approach is retired — a probe must never write the action byte it is trying to observe.

The boot-window build

The rule and the bytes

The idle-gap predicate cannot see a reboot, so this build measures the one thing a reboot always resets — uptime:

0x20000: push.w {r4-r11, ip, lr}   2d e9 f0 5f
0x20004: ldr    r0, [pc, #0x18]    06 48         ; MODE
0x20006: ldrb   r0, [r0]           00 78
0x20008: cmp    r0, #0             00 28
0x2000a: beq    0x20030            11 d0         ; wired: pass
0x2000c: ldr    r1, [pc, #0x14]    05 49         ; NOW
0x2000e: ldr    r2, [r1]           0a 68
0x20010: cmp    r2, #0             00 2a
0x20012: beq    0x20030            0d d0         ; no tick: pass
0x20014: movw   ip, #2500          40 f6 c4 1c

0x20020: .word  0x20000378         78 03 00 20
0x20024: .word  0x200004A8         a8 04 00 20
0x20028: .word  0xbf00bf00         00 bf 00 bf   ; pad, never reached
0x2002c: .word  0xbf00bf00         00 bf 00 bf

Rule: drop while mode ≠ 0 and 0 < now ≤ 2500 ms. Nothing is remembered, so a reboot cannot hide from it, and nothing can latch.

Device stateWhat happens

wireless, up > 2.5 spasses — byte-for-byte stock behaviour
wireless, up ≤ 2.5 sdropped — this is the window the build is testing

Reading the test

Reading the test is deliberately blunt: keys silent for ~2 s after a wake means the wake does restart the MCU, the window is now real, and the leak is gone. Typing immediately, still CapsLock means the wake does not restart the counter — the window is somewhere else, and this build is a no-op rather than a fix.

Built (2026-10-24, not flashed): analysis/fw_bootwin.py → out/fw_bootwin_remap.bin 9c4aa001… and out/fw_bootwin_remap.exe 5046b698…, on top of the arrow-cluster bake, so the cluster and Fn+Right survive. 47 image bytes differ from the bake (4 hook + 43 stub bytes; the rest of the stub was already zero) and 59 in the exe. --boot-ms retunes the single immediate.

Why not simply combine both rules: the idle gap would arm on a stale press time after a reboot and the boot rule would then be redundant; keeping one rule per build is what makes the flash an experiment instead of a guess.

The macro guard — stop the factory usage, not the clock

2026-10-25, user test: the boot-window build was flashed and the leak survived. The same physical key with a plain remap instead of a macro works on the very first press after a wake. So the window is not the key, not the wire mode, and not "all configuration is late" — it is the macro path only.

Both timed builds were structurally unable to fire, which is why they changed nothing: there is no wfi in the main poll block 0x10DE0–0x10E60, so the millisecond tick never stops and an idle-gap timer can never arm; and the only self-reset in the image is the HardFault path 0x518C, so an uptime window is never true at a wake either. The hook and stub did execute (the marker build proved that by breaking the pipeline), so the predicates, not the sites, were inert.

Where the wrong usage comes from: the per-event handler 0x5D28 stages the key's factory usage from table 0x16B3E at 0x5D4A before the configured record is considered. That table is indexed by scan position — the macro key (id 0x30, position 18) stages 0x39, CapsLock. A plain remap is a single 4-byte catalog record, so it replaces the staged byte on the first press. A macro is not: kinds 9/0xA/0xB branch at 0x5EC6 into the player arming code at 0x6ACE (macro index in catalog record byte 1, data through flash table 0x9C00 + idx*4, player flags 0x200000B0/0x200000B3), so until that structure is playable the staged factory byte is what reaches the host.

The rule

press flag 0x20000090not 1 (a release)stock
macro player 0x200000B3not 0 (playing)stock
staged action 0x2000008Cnot 0x39stock

No clock is read at all. The guard usage is derived by the builder from --key CapsLock (id 0x30 → factory usage 0x39), not hardcoded.

Why it cannot type the wrong key

Worst case is that one usage produces nothing while the player is idle. The press never enters the funnel's 5-slot pressed list, so its later release is a harmless no-op rather than a stuck key; wired mode, releases, and every other action are byte-for-byte stock. The old dead-window stub is overwritten, so the arrow-cluster bake underneath is preserved.

Built (2026-10-25, not flashed): analysis/fw_macroguard.py → out/fw_macroguard.bin 0eb37a76… and out/fw_macroguard.exe e93edd7d…, on top of the image the keyboard runs now (4dd3201c…). 48 image bytes differ from that base. The builder refuses any base it does not recognise, any key whose factory usage is not a bitmap usage, and any funnel body that reads r0–r3 before writing them.

Test: wired — the key still runs the macro. Wireless — wake and press this key inside the ~2 s window: it should type nothing (today it types CapsLock); after the window it runs the macro. Any other key inside the window is unaffected.

The result: it did not fire

2026-10-25, flashed: the guard did not fire. Wired behaved normally, including Fn+this key toggling caps; on a wireless wake CapsLock still arrived. Worse, Fn+this key then appeared to reset the MCU (boot lighting) and repeated presses during the wake froze the keyboard. Two conclusions: the leak never passes through the funnel hook, and the Fn/macro branch can fault while the wireless tables are not yet valid.

Removing the fallback instead of the report

If the hook never sees the byte, stop looking for the byte on the wire and delete the thing that produces it. The leak is one event — the first press after a wake, handled while the per-key record is still empty — and that state has its own branch: 0x5E66 (kind == 0 && settings == 0) falls into 0x5E80, which emits the factory usage that 0x5D4A staged a few instructions earlier. A configured remap overwrites the staged byte; a macro does not, which is exactly why only the macro key leaks.

The 0x5D54 bail is safe to remove because it only guards positions with no factory usage: all 67 zero bytes of 0x16B3E belong to non-physical scan slots, and every one of the 61 physical positions stages a usage. After the patch the empty-record path emits nothing for any key, and a configured macro still runs because the record path (0x5EC6/0x5ECC) is untouched — no clock, no mode byte, no state.

What it costs

Fn+this key no longer produces CapsLock: that passthrough read the same factory byte. Everything else is stock, including wired mode, the arrow bake underneath and the code-option/version words. The wireless Fn+this-key reset seen with the guard build is still not explained, and this patch does not touch that branch.

Result (2026-10-25, flashed): the leak is gone. Waking with the macro key types nothing; the next press runs the macro. Nine bytes had done the job, on the image that was then on the keyboard.

The follow-up bug that fixing it exposed: that base also carried the first build's 30 s / 2 s idle dropper, because each build had been layered on "the image the device runs" to keep the arrow cluster. The dropper never saw the wake leak (that path skips the funnel) but it did see ordinary typing, so after 30 s idle the first presses in wireless were swallowed. Layering is what smuggled it forward; the release build starts from the clean bake3 instead, and the builder now refuses a base whose 0x127E0 is not the stock push.w unless --allow-hook is passed.

Making the first press work, not just silent

The release build stops the wrong key from going out: the first press after a wireless wake emits nothing. It does not run the macro that key carries. Doing that is a dispatch problem, not a keymap one, and the 2026-10-26 read below moved the target twice.

The dispatch map (verified)

Every key event reaches one dispatcher. It reads the per-key record kind from [sp,#8] and tail-branches:

record kindhandlerwhat it is
9, 0xA0x5A00the position-indexed handler with the media/Fn-action path
0xB, 0xC0x7500the second special handler
anything else0x5D28the generic handler — the one that stages the factory usage at 0x5D4A

And immediately before that dispatch there is a gate at 0x37E2: it reads one byte, 0x2000008F, and if it is non-zero it skips the kind dispatch entirely and goes straight to 0x5D28. So a macro key whose record is kind 9 is handled as an ordinary key whenever that byte is set — which is exactly the observed "factory CapsLock" behaviour. All nine references to 0x2000008F in the image are reads; no direct store was found, so its writer is still computed-indirect, like 0x5b1d6c was.

Why "reload before scanning resumes" was dropped

The plan was to move the per-key load ahead of key dispatch. That route is falsified: the loader 0x58D0 has exactly one bl caller in the whole image, 0x153EC, inside the boot init — it runs once, then the code falls into the main loop at 0x153FC. There is no wake-time reload to move, and no other call site to reuse.

That also retires an older note on this page: the link-up re-init does not rebuild these tables. 0x59F0 is a GPIO pulse helper (bl 0x5468, b.w 0x5450, both OR-ing bits of 0x40038000), not a loader.

Route 1 is now the cheapest and the most direct: the gate is the thing that decides whether a macro key is treated as a macro, so if it can be put in the right state at wake, no new state machine is needed. The remaining unknown is its writer, which is a single targeted scan rather than a design.

The writer is indirect — so probe the gate instead

Three sweeps found no writer for 0x2000008F: literal-based stores to every 0x200000xx base, taint-tracked add/mov up to offset 7, and calls whose argument points into the block. Nothing. It is written indirectly (or by a structure copy), the same wall 0x5b1d6c hit.

So the gate is tested directly instead, with two bytes: force the kind dispatch unconditionally and see whether the first press runs the macro.

0x37E6  18 B1   cbz r0, 0x37F0     before
0x37E6  03 E0   b   0x37F0         after (record kind always decides the handler)

Built (2026-10-26, probe): analysis/fw_gate.py → out/fw_gate.bin 382eea5a… and out/fw_gate.exe 69885973…, on top of the released image (ecb236fb…), 2 bytes. Read it in this order:

  • wired: Fn+Right, Fn+Left, Fn+1 and the macro all unchanged → the gate is safe to ignore;
  • wired: any of those changes → the gate has a purpose and this route stops;
  • wireless wake with the macro key runs the macro → the gate was the first-press cause;
  • wireless still types CapsLock or nothing → the gate is not the cause.

Probe result: the gate is not the cause

2026-10-26, flashed: wired behaviour was unaffected, and the wake still does not run the macro on the first press — but it no longer emits CapsLock either, so the fallback fix still holds. That kills the gate hypothesis: with the gate forced open, a kind-0 record still lands on 0x5D28, which is exactly what the gate was doing for it anyway.

What that leaves is the original reading, now with a sharp edge: the per-key record really is not populated for the first event. The only code that fills it is the boot-time loader 0x58D0 — one caller, 0x153EC, inside init — so the first press must be arriving before init finishes, i.e. the key subsystem (at least) re-initialises on a wireless wake. That also explains the boot lighting seen on an earlier build.

The consequence: no table edit can make that event run its macro, because the information it needs does not exist yet. The only universal fix is to hold the event and replay it once the record is populated — the deferred-press route — using the validity byte 0x2000386E + id == 5 as the "ready" signal, with a ~300 ms deadline so a never-ready record cannot mute a key.

The deferred press

Two hooks and 148 bytes of stub:

sitestockpatchedrole
0x5E8000 f0 10 b8b.w 0x20000capture: wireless and an empty record → remember position, event byte, timestamp
0x153FCbl 0x6BCCb.w 0x20028poll: the main loop's first call, so it runs continuously; replay is bl 0x6BCC then b.w 0x15400

Replay restores the position into 0x200000F4+9 and the event byte into +8, sets sl so the handler's macro branch is eligible, and calls 0x5D28 — the real handler, so the macro arms exactly as it would on a later press. Readiness is the handler's own source of truth: record kind at 0x200024AE + id*4 becomes non-zero once the loader merges the key's configuration.

Built (2026-10-26, second revision): analysis/fw_defer.py → out/fw_defer.bin 64fc7d13… and out/fw_defer.exe b592f972…, on the released image (ecb236fb…); 146 bytes differ.

Two things changed after the first revision was flashed and did nothing, which is itself informative: the capture no longer tests the mode byte (during a wake the switch debouncer can still read 0, and the branch only fires when a record is empty, which never happens in wired mode), and readiness now means a special record — kind 9..0xC — rather than any non-zero kind, so a factory record can never be replayed into a CapsLock.

Failure modes stay quiet: no special record within 300 ms → nothing is typed, exactly as today; sl or the internal gate declining the macro → the staged usage is already 0x00, so still nothing. The one structural risk is context: the handler normally runs from the scan IRQ, and here it is called from the main loop, so a real key press could interleave in the window between the restored event and the call.

Result: still silent (2026-10-26, flashed). The first press after a wake still does nothing and the macro runs from the second press. So the capture almost certainly never ran — which points at the first event not carrying an empty record. That matters, because the old CapsLock may have been the staged byte (0x2000008C) sent downstream after the handler returned, not an emit inside 0x5E80 at all. A third revision of the script (7f074085…, readiness = any non-zero kind) is built and not flashed; the emit probe had already shown the emit was downstream.

One byte separates those two: put the factory usage back at 0x16B50 and leave everything else (the exit at 0x5E80, the removed bail) exactly as the release has it. If CapsLock returns, the staged byte is emitted downstream and the capture belongs before 0x5D4A; if it stays silent, 0x5E80 is the emitter and the replay failed for another reason. That probe is analysis/fw_emitprobe.py (c107cf76… / 6d098fbe…).

Result: CapsLock came back (2026-10-26). So the staged byte is emitted downstream, and nothing at 0x5E80 could ever have affected it. Together with the capture never firing, that says the macro key's record is a macro kind and its handler is 0x5A00, not 0x5D28 — and 0x5A00 has the same factory staging at 0x5A22 plus an inner gate of its own.

The inner gate in 0x5A00

0x5AA2  ldrb r2,[r2]        ; per-key byte in the settings page 0xB000
0x5AA4  cbz  r2, 0x5AAE     ; no settings -> the arming path
0x5AA6  ldr  r2,=0x2000008F
0x5AA8  ldrb r2,[r2]
0x5AAA  cmp  r2,#0
0x5AAC  bne  0x5B18         ; a configured key is DIVERTED while 0x8F is set
0x5AAE  ...                 ; arming path

A key with settings is diverted whenever 0x2000008F is non-zero, and the diverted path never arms the macro; the staged factory byte then goes out downstream. That is the observed behaviour, and it also explains why the dispatcher gate probe changed nothing: that gate sits earlier and both branches end here.

Built (2026-10-26, probe): analysis/fw_armgate.py → 0x5AAC 34 d1 → 00 bf (drop the diversion), image c63367bf…, exe d9347ace…. If the macro runs on the first press after a wake, this gate was the cause. When 0x2000008F is zero nothing changes at all, so wired behaviour is untouched.

Result: no change (2026-10-26). The macro still waits for a second press. That, plus "no CapsLock", says the diversion was not being taken for this key — the gate is behind a condition this key does not meet.

Where the factory binding actually comes from

Scanning for every reader of the factory table found the real mechanism, outside the key handlers entirely. A filler function at 0x10978 loops over all 168 scan positions:

0x109AC  ldrb r0,[r6,r4]        ; id   = 0x16A96[position]
0x109AE  ldrb r1,[r5,r0,lsl #2] ; kind of that key's settings entry
0x109B2  cbnz r1, 0x109BA       ; already has settings -> leave it
0x109B4  ldrb r1,[r7,r4]        ; usage = 0x16B3E[position]  (factory)
0x109B6  bl   0x109D8           ; synthesise a record from that usage

and 0x109D8 writes into 0x200026AE — the settings mirror, not the catalog. So on a settings apply, every key that has no entry yet is given a synthetic record built from its factory usage. For the macro key that is 0x39: CapsLock. Its own settings arrive after that pass, which is exactly the "first press is factory, second press is the macro" behaviour, and it is why every hook placed in the key handlers stayed silent — the press is answered from tables this filler had just populated, and the deferral never saw an empty record.

Consequence for the goal: no table or handler edit can make that first press run the macro, because at that instant the firmware genuinely does not have the macro yet. The two honest ways forward are to bake the per-key settings into the image (so they exist before the filler runs — the Tier-B route, which needs the settings record format reversed) or to accept the current behaviour.

Accepted (2026-10-26)

Accepting it. What ships is: the first press after a wireless wake produces nothing, and the next press runs the macro normally. That is a deliberate, bounded limitation — a silent key instead of a wrong one — and the goal of "the macro runs on that first press" is parked behind the settings-format work in the backlog, not behind another key-pipeline hook.

Everything tried on the way is recorded above so it is not repeated: the report funnel (0x127E0), the dispatcher gate (0x37E6), the inner gate in 0x5A00 (0x5AAC), the empty-record branch (0x5E80) with a deferred replay, and the staged factory byte. Each was falsified on hardware; the emitter turned out to be the settings filler at 0x10978, which runs before the press is handled.

Not established

  • Where exactly the firmware's own wake window opens and closes: the reply handler's ready path (0x1EAE, lighting 0x4B) is the best static candidate, but its call frequency is not proven, so the patch does not hook it.
  • Whether the apply window is really 2 s in every configuration (2.4G vs BT, dongle vs host) — the constant is the user's measurement, not a firmware value.
  • Whether the idle gap that matters is the link's or the host's; 30 s is a guess that has to be tested against the keyboard's actual sleep timeout.
  • What the host sees for a suppressed press: nothing is staged, but the report cycle still runs; a stale report is possible in principle, not observed.
  • Which input was wrong — answered. None of the three: the leak never passed the funnel at all. The handler emitted the staged factory byte for an empty per-key record, which is why every timed predicate and the funnel guard were inert.
  • What the per-key tables hold during the window — less relevant than it looked: the loader 0x58D0 runs once at boot and has no wake-time caller, so the first event is most likely routed to the generic handler by the dispatch gate 0x2000008F rather than reading an empty record. See the first press.
  • Why the guard build reset the MCU in wireless. Fn+this key rebooted (boot lighting) and repeated presses froze the keyboard, which points at the Fn/macro branch faulting while the wireless tables are not valid — a bad dereference, not a timing bug. Not explained statically yet, and the new build does not touch that path.
  • Whether the empty-record branch is really the one that fires first — confirmed on hardware 2026-10-25: the nine-byte build removed the leak, so that branch was the source.
