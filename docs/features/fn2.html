A second Fn key (Fn2) — feasibility of a second Fn map in RCDATA 4000

Status: feasibility study (2026-10-22, static) — realistic as a level-3 code hook in 2–4 days plus 2–3 flash cycles; layer 2 already exists and is wired into the dispatcher but unreachable; the Fn flag writer is the one unresolved gate · Read when: asking for a second modifier key with its own map, deciding between momentary Fn2 and a layer toggle, or budgeting the first patch that adds code

What it is

The question: can the board have a second Fn-like modifier — a key that, while held, makes other keys resolve through a different 51-row table than Fn uses?

Verdict: yes, and it is smaller than it sounds — but it is the first patch that must add code. There is no table-only route, because the Fn map is chosen by a persistent OS-mode byte (0x200000AE), not by which modifier is held. What makes it cheap is that the second map, the table-selection code and the blank flash for a hook all already exist.

What is already there (fact)

The dispatcher 0x2FF0 loads all four layer bases up front and has a branch for every mode value, including the one nothing can reach:

2FF4  ldr  r4,[pc]        ; r4 = 0x20000088   keyboard object
2FF6  ldr  r5,[pc]        ; r5 = 0x16C3E      layer 0
2FF8  ldr  r6,[pc]        ; r6 = 0x16CA6      layer 1
2FFC  ldr  r7,[pc]        ; r7 = 0x16D0C      layer 2
2FFE  ldr  r8,[pc]        ; r8 = 0x16D72      layer 3
3006  ldrb r0,[r4,#8]     ; Fn-held flag (0x20000090)
3008  beq  0x30A2         ; no Fn: restore path
300A  bl   0x7378         ; row = search(layer0.byte0 == usage), 0xFF = none
3016  ldrb r1,[r4,#0x26]  ; OS mode byte
301C  cmp  r1,#1  3020 cmp r1,#2  3024 cmp r1,#3
302A  out = layer0[row*2+1] -> [r4,#4]
3034  out = layer1[row*2+1] -> [r4,#4]
303E  out = layer2[row*2+1] -> [r4,#4]   ; mode 2: reachable, never selected
3048  out = layer3[row*2+1] -> [r4,#4]
  • Layer 2 is already wired and dead. 0x303E selects 0x16D0C when the mode byte is 2, and nothing writes 2 — 0x2AE4 writes only 0/1/3. That is a free 51-row second map, already the right shape; its byte 1 column is currently identical to the Mac layer.
  • One input mapping serves every layer. The row index always comes from layer 0's byte 0, so an Fn2 table only needs its byte 1 column edited — no new input map, no relocation, no stride change.
  • Nothing caches the mode. The byte is re-read on every event at 0x3016, so a momentary change takes effect on the next key event and reverts cleanly.

The smallest design: a momentary mode override

Rather than adding a second flag and a fifth table, borrow the unused mode value while the key is held:

  1. Sentinel usage. Give the Fn2 key a usage value in its catalog record that the host ignores — the trick that already makes Fn work (cmp r0,#0xaf at 0x147B6). The value must also exist in the pair table on a spare id, so the usage→id lookup at 0x327C still resolves.
  2. Momentary mode write. Hook the key-event path: sentinel pressed → save the current mode byte to a spare RAM byte and write 2; sentinel released → restore the saved byte.
  3. Fill layer 2. Edit its byte 1 rows at 0x16D0C+, up to 51 actions.

No dispatcher edit, no new table, no relocation: roughly 60–120 bytes of Thumb in blank flash, one RAM byte and one key role. The failure mode is benign: a missed release leaves the mode at 2, so Fn keeps returning the Fn2 map until the key is pressed again or the board resets — visible, and recoverable without a reflash.

The gate: how a physical Fn press sets its flag

The dispatcher's gate is a plain zero/nonzero test on 0x20000090, but its writer is not pinned. In the main code the only literal references are a read at 0x10D8 and a clear at 0x233C, and the only immediate-offset store found is the macro player's group-0x30 step (0x53D4/0x53D8). That pattern points at a generic modifier-group store through a computed base, which an immediate-offset hunt would miss.

Resolve it by reading the [base+4]==0xAF branch at 0x147C4 and the clear at 0x233C — half a day to a day. Two outcomes:

  • Fn is one entry in a generic group mechanism with a free group code → Fn2 becomes simpler than the design above, possibly a data edit plus a group assignment.
  • Fn is bespoke → keep the design above, and detect Fn2 at the actuation state instead (0x32AC; per-key actuated bit 15 of 0x200031AE), which gives explicit press and release at a slightly hotter code site.

Limits and costs

  • Same row ceiling as Fn. The lookup only resolves usages present in layer 0's byte 0, so app-remapped keys fall out of the Fn2 path exactly as they fall out of Fn today. Fn2 can only map the 51 stock usages.
  • Mode 2 is visible while the key is held. Only the base+0x26 addressing form is confirmed; absolute movw/movt readers of 0x200000AE were not ruled out, so any code keyed on the OS mode may misbehave during the hold.
  • Precedence is a design decision, not a detail: Fn2+Fn, Fn2+S/D/A (the Mac/Windows/Android combos, which overwrite the mode byte), and Fn2 held across a wireless dead window all need a rule before the first write.
  • Every iteration is a flash that wipes the NVM settings, with no readback and no debugger.
  • No app-side route. The config app cannot express a second modifier and the NVM records have no slot for one, so Fn2 exists only in firmware.
  • Cheap fallback if momentary semantics do not matter: a key that toggles the mode byte 0↔2, so plain Fn switches maps. Less code, but global sticky state that fights the Mac/Android modes.

Ladder, following the level-2-first rule: prove the table swap with a data-only change first (point Windows mode at layer 1 and confirm Fn outputs change), then add the sentinel toggle, then fill layer 2. The first two rungs need no new code.

Not established

  • How a physical Fn press sets 0x20000090 (the gate above).
  • Every reader of the mode byte, including any built with movw/movt.
  • Whether the event path reports press and release distinctly enough to hook, or whether the actuation state is the only reliable site.
  • The whole page is static: no Fn2 code has been written, built or flashed.
