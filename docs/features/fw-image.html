Firmware image — the embedded RCDATA 4000

Status: core decode verified (vector table, regions, product string); checksum formula + version gate now verified as tool-side runtime compare (nothing embedded in the image); no radio/companion-chip path (negative evidence) · Read when: touching analysis/decode_fw.py, interpreting anything at a flash offset, planning a patched image, or asking whether the board carries 2.4G/Bluetooth

What it is

  • RCDATA id 4000 from the pinned exe — 516,096 bytes (0x7E000), extracted by analysis/probe_pe.py to analysis/out/rcdata_4000.bin. Decoded by analysis/decode_fw.py; full report analysis/out/fw_decode.txt, strings fw_strings.txt.
  • Cortex-M3-style firmware image (fact): vector table at 0x0, Thumb code, SNiX USB-device library inside, ASCII product string MINI60HE MAX. RCDATA 4010/4016 name the tool-side target: SN34F280, file SN34F280_User.hex.
  • Verified Thumb, not ARM: every vector address has bit0 set and is 4-misaligned (ARM requires the opposite); in-window thumb disassembly yields 50–57 valid instructions before the first invalid vs 4–28 for ARM. push.w/mov.w/muls appear ⇒ not a Cortex-M0.

Vector table (fact)

v[0]  SP = 0x200076F8          # SRAM top — RAM begins 0x20000000
v[1]  Reset     0x204          # real code: sets SRAM-backed bit16 x2, bx jumps
v[3]  HardFault 0x518C         # real handler: dsb + fault-capture writes
v[15] SysTick   0x10BA8        # push {r4,lr}; bl 0x3FE8
default IRQ     0x22C          # "b ." self-loop stub
real IRQs       19, 27, 34, 40, 51, 54  (0x10780, 0x23E4, 0xFC8, 0x204C, 0x8FF0, 0x10F08)
v[61]           0x205C         # writes 0xFFF via [r1+0x3C]
tail damage-stub region: 0x21A..0x22C all "b ." self loops

The reset handler thumbs through two 4-byte writes (bit16 clear then set of a config word) before jumping through a loaded pointer — periph-clock config, exact target unverified.

Product identity (fact — the file-name trap closes)

  • "MINI60HE MAX" occurs twice in the firmware itself (0x12060 in code/literal context, 0x16F7E inside a string-table with length byte 0x58) — the keyboard's own USB strings; RCDATA 4013 pins the tool build to 2026/01/21.
  • The exe's file name "Mini60 HE Max"/UI strings are no longer independent claims for product identity.

No radio or companion-chip path (negative evidence)

Scanned by analysis/probe_radio.py → out/probe_radio.txt; regenerable, image hash pinned.

  • No wireless vocabulary: zero ASCII and zero UTF-16LE hits for Bluetooth, BLE, 2.4G/2G4, Wireless, PAIR/PAIRING, DONGLE, nRF, ESP32, RADIO — and zero for UART, USART, SPI, I2C, IIC.
  • No bus to a second chip: the recursive-descent map (out/fw_code.txt) reaches nine peripheral blocks only — USB device (0x4001F0xx/0x4001F8xx), LED driver (0x4001B1xx/0x4001B2xx), Hall AFE (0x40027000), four GPIO banks (0x40037000/0x40038000/0x40039000/0x4003A000), one clock/config word (0x4002103C) and the flash/EEPROM controller (0x40057000). No serial controller appears.
  • One HID interface (HID Interface, 0x18044); the USB stack's strings are only its own range-check messages.
  • Size fits a wired build: ~90 KiB of code/data in three blobs, ~416 KiB zero fill — a BLE stack would be another large blob, and there is none.
  • The updater agrees: one hardcoded wired identity (VID/PID) and an all-wired SONiX chip table; no pairing/dongle command in the AA 55 set.

Caveat: this is negative evidence about the MCU image, not knowledge of the PCB. If the board does carry 2.4G + Bluetooth, it is a separate RF SoC with its own firmware and updater — it would need its own USB path, because this SN34F280 image has no link to drive it. Board markings, the module shield or the vendor spec settle it.

Checksum & version fields (compare side verified; image carries none)

Verified tool-side (2026-10-22)

  • No checksum sits in the image (fact): sum16/sum32/crc32/negsum16 over five windows, searched at every 4-aligned offset — zero matches. Only the tail magic exists. The load-time checksum is tool-side, no firmware byte carries it: fn 0x40A7D0 = plain 32-bit byte-sum Σbuf[i] over len bytes (SN8 path); fn 0x40A800 = big-endian-16 word-sum Σbuf[i] + (buf[i+1] << 8) per 2-byte pair over len, truncated to 16 bit at return (movzx eax,cx) — fed by the bin/hex loaders and displayed as 'Bin File Check Sum : %.4X' / 'HEX File Check Sum : %.4X' (refs at 0x424487/0x42446E in fn 0x423F80) with the computed word in [dlg+0x42C]. Any future patched build must keep the loader-side sum consistent with what the ISP flow tells the device, or at least survive the tool's version/sum screens.
  • Version gate verified: dispatcher fn 0x401100 reads the per-chip record pointer array at 0x5B30C7 (stride 0x33, variant byte array at 0x5B30B2), takes the record's +9 dword as a word-index, reads the version dword at fwbuf + idx*2 (fwbuf = [dlg+0x1E44]), and compares it against the 4 device-reported version bytes (cmp dword, then 4 byte-diffs at 0x40144C..0x401486) — mismatch ⇒ 'Firmware Version is not for this chip!!' (0x589840) / SN8-variant ⇒ 'Firmware Version in SN8 file does not match that of USB Device!' (0x589A90). The version-offset word index itself lives behind the record +0x1F pointer's member +0xD (fn 0x423F80 stores it in [dlg+0x1B94]).

Still hypothesis

  • Hypothesis narrowed: the absence of any version/checksum constant in the image strengthens 'tool-side compare against the device read-back' — so a patched firmware needs its version dword (at the record index) and loader checksum updated in step. The device's bootloader-side pw/table constants are NOT part of this user image (all four candidate encodings absent — V1, out/isp_pw6.txt).
  • The 0x7E000 span (512 KiB − 8 KiB) is consistent with a 512 KiB flash device minus an 8 KiB bootloader reserve (CheckBootLoaderID), but the device's true flash size is unverified — the image may equally be a fixed-size buffer around a ~0x18600-byte build.

Traps

  • 0x00, not 0xFF, is the empty state in this image. Treating erased-flash conventions ("0xFF fill") as read on this image sends every scan to nothing: no 0xFF page exists anywhere.
  • "Firmware" is a short label for a candidate. Identity is strong (vector table + USB stack + product string) but the chip model SN34F280 comes from the tool's RCDATA, not from the image.
  • Vector-entry stubs are literal-pool territory. Between the real vectors the bytes at 0x22E..0x23A mis-decode as instructions (and r0, r4, #0x81000000…) — that is pool data, not code; do not disassemble blind forward from a stub.
  • The two code-island gaps are real. Any patch address lifted from one blob assumes one contiguous code blob — the 0x9810–0xAE10 and 0xB000–0xBA00 zero gaps split it, and offsets cross-reference per region only.
