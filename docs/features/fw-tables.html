Keymap & LED tables — the 0x16E00–0x185E8 band of RCDATA 4000

Status: recon verified (61-key universe + three layout/grouping tables + LED-engine tables classified by byte evidence); the id→usage table, layer tables, actuation constants and change filter are now documented on the phase-4 key-pipeline page · Read when: decoding a key id, planning key remapping or RGB mods, or touching analysis/fw_feat.py

What it is

  • The table band inside RCDATA 4000 (same image as the Firmware image page), classified by analysis/fw_feat.py; full report analysis/out/fw_feat.txt, regenerable with python analysis/fw_feat.py.
  • In this band 0x5A ("Z") is the unused-slot filler byte and 0x00 acts as a delimiter/terminator — neither is an "empty flash" convention.
  • Band start 0x16E00 is the tail of the string/font/gradient zone; the region 0x18140–0x185E8 additionally carries real HID report-descriptor item bytecode (19 e0 29 e7 75 01 95 08 81 …, usage-min/max E0–E7 = modifier bitmap) interleaved with other data.

Key universe (fact)

  • Exactly 61 key IDs 0x01–0x3D, contiguous, no gaps — consistent with a 60%-class ANSI board. Byte-verified: the walk array below enumerates all 61, and the union of all three layout tables is {01…3D} with zero missing values.
  • These are internal layout key IDs, not HID usage codes. The id → HID-usage conversion lives in the band at 0x16DD8 (120 entries, sentinel id 0x7D) — see Key pipeline & remap surface, which also carries the scan/actuation/debounce findings.

Layout tables (fact)

                                    0x5a filler padding the remaining slots to 0x1704C

                                    terminated by 0x00 at 0x170AC; 8 groups (6,10,8,9,10,5,1,10)
                                    covering 59 of the 61 keys (2x missing: 22, 3d)
C LED groups      0x175C1..0x1762B  group ids 00..0D in ascending order, each followed by
                                    1..4 member key ids (all >= 0x0e, so id-walk is
                                    unambiguous), 0x5a padding between/inside records;
                                    14 groups, 58 of 61 keys covered
W pair table      0x16FF6..0x1700D  12 raw pairs (key,partner), first partner is the
                                    0x5a wildcard: (1c,5a)(1d,0e)(1e,0f)(1f,10)(20,11)(21,12)
                                    (2f,09)(2e,08)(2d,07)(24,15)(23,14)(22,13)
(cell records)    0x174B9..0x17598  16-byte-stride records of <=4 (a,b) pairs, 0-padded —
                                    a second grouping view, semantics open
  • C groups read as a diagonal sweep: each crosses the walk blocks once (e.g. group 9 = 09 12 25 2b 39; group 13 = 0d 0e 28 — the right edge and then wrap).
  • B lines likewise pick ~one key per walk block (line 7 = 01 1b 1c 34 3c 3b 29 28 0e 0d shows symmetric edge pairs). The A-blocks are therefore not proven to be physical rows — treat block↔row as open.

Traps

  • Do not index C at fixed stride — early records look 8-byte-aligned (5a 00 1b 1c 34 35 5a 5a) but member counts vary; parse by walking expected group ids 00..0D.
  • Member bytes ≥ 0x0E always. That is what makes the id-walk parse unambiguous; if a future variant shows a small member byte, the parser needs a better discriminator.
  • 0x5A vs 0x00 have opposite roles (filler vs delimiter); stripping both blindly corrupts group boundaries — B's line split needs the ≥2-consecutive rule, A needs byte-0 as terminator.
  • Key ids ≠ HID usages ≠ matrix coords. No conversion table was found in the band; assuming 0x02 lovercase etc. without the converter will produce wrong remaps.
  • Physical-grid placement is open. The diagonal sweep pattern suggests LED-zone geometry, not key rows; pin the grid against code (phase 4) before claiming a physical key position for any id.
