ISP protocol — the updater's feature-report protocol over HID

Status: command table + frame format + uploader + code-option + finish-floor verified from the pinned exe; 2026-10-22 corrections: the 0x2x-family rows are bare cmd AA 55 (no 05 prefix), the pw short frame = 8B 02 AA 55 00 + payload at *(flowCtl+0x1c), the pw echo gate returns 5-on-match/4-on-mismatch vs stored global 0x5b1d6c (initial 0xFAFAFAFA poison, writer register-indirect), SZK671F is one chip-name-registry member across 5 protocol variants, and the EVT/I2C open item is closed (absent from the exe). Still open: which conversion of RCDATA 4007 lands on the wire (4 candidate encodings) · Read when: interpreting anything in the ISP zone, planning a controller reimplementation, or touching the version/checksum story

What it is

  • Foundry: the phase-1 strings guessed feature reports; the disassembly refutes both guesses. The protocol sends HID output reports through HidD_SetOutputReport (IAT slot 0x55B1F8, always reached via jmp [0x55B1F8] at 0x429744, whose only incoming call is 0x4287C2 inside the send wrapper 0x428680) and reads echoes with HidD_GetFeature through read wrapper 0x428810. No other HID transfer type is imported.
  • Rule of the exchanges: every frame is an 8-byte output report (report-ID 0 prepended before buf). Almost every command ends in the sequence {0xAA, 0x55, 0x00} at buf[1..3]. No SetFeature-side command carries an 0xAA55 — that triad is the device→erase-flow side, from protocol slots referenced only by the bulk gateway at 0x5bcea8 (see io_sites window 0x4029FE for one example). Evidence out/io_sites.txt, first window 0x4029FE.
  • Demand: responses land in a caller-fed expect buffer instead of a fixed echo template. Each of the twelve caller sites (0x40BC8C, 0x40CA02, 0x40CA5D, 0x40CB2B, 0x40CC02, 0x40CCEC, 0x40CE60, 0x40CF58, 0x40D0FE, 0x40D15F, 0x40D278, 0x40D2C4) passes its own wanted-echo and retries (bounded by evt nb/d5260) inside 0x40D310; windows 'below'.

Transport wrappers (fact)

  • Send wrapper 0x428680 (stack 0x1108, cookie esp+0x1104): opens the interface path for device [0x5b6d48] with CreateFileW (share mode 3 first, retry without the extra-flags open on failure, dis 0x4286C0/0x4286D9), zeroes a 4 KB scratch, formats the log lines FeatureStatus : %d / DeviceHandle : 0x%x (0x55FBB8/0x55FC24 via CString 0x52ACE5), caps the send length at 0x1000-1 and calls 0x429744 → jmp [HidD_SetOutputReport]. Ret sete.
  • Read wrapper 0x428810 (stack 0x1008, cookie esp+0x1004): same open dance, sink buffer, jmp [HidD_GetFeature] at 0x4288B7, then CompareDevice...Revision 0x5aae50 += 1 accounting per call, log via 0x55FBE4 FeatureReportByteLength : %d, sete return.
  • Pace helper 0x40b520: Win32 Sleep(eax) — sends are typically followed by two Sleep(10) ticks, then the read.

The 0x4039C0 upload flow (fact)

  • 0x4039C0 is dispatched per-chip with 0x33=51 stride records at [0x5b30c7] (chip-slot array). It reads the record's two UTF-16-word fields (+0x27/+0x2B/+0x2F) then builds the command schedule; a null data pointer at [ecx+0x14] bails early (branch to 0x4043fe).
  • Order of helpers inside: 0x40b740 (12B variant of send 0x4029E0-zone) → 0x40a550 restart-ok wrapper → progress-bar 0x407/0x408/0x40B/0x406 calls driving 0x55B870 (MFC progress) with 0..100 ranges; then command helpers 0x40b950 (0x22-zone), 0x40bb80 (0x07-zone), 0x40bea0 (0x27-zone), 0x40c360/0x40c6f0 (0x29/0x28-zone), 0x40ba60 (code-option variant at +0x3fe0), 0x40a7d0, etc. The chain terminates in 0x40A510 (SetDlgItem/margin) and 0x40a550 (restart ok).

Per-flow ops and read-back gates (fact)

  • Per-flow ops confirmed via flow dispatch: erase disconnect (0x40A1DEesp-state clone), erase connect after (0x40B8AB-zone), 64-byte enable-program chunks (0x40BAA9, i.e. the "chip Erase..." of 0x589370), 0x40BCE0/5-zone ('0x408FDF' verify stack, '0x409D40' verify stack), '0x409D40' per-page verify where 0x40C360/0x40c6f0 read-back is re-fetched off the transport wrapper.   • Show-waves of the 0x4039C0 flow: 6-step reconnect checkpoints run through 0x40BEA0(9) and 0x40c6f0 — the convertor masks of read-back protocol gates in the ISP zone.

Command table (fact)

Wire formats verified at send sites (set_digest.txt); in every row below the cmd byte is wire index 0, AA 55 indexes 1–2, payload follows at index 3+: 01 AA 55 Get FW Version (0x40B60B, 0x40B6C6); 02 AA 55 Compare Password (0x40B7A1, long 0x40 form 0x40BB07); 03 AA 55+algo Set Encryption (0x40B8AB, 10-byte form 0x40BA3C); 04 AA 55 Enable Erase (0x40B9AD); 05 AA 55+addr+64B page Enable Program (0x40BE2D, data frames 0x40BAA9); 06 AA 55 Get Check Sum (0x40BF17, 0x40C06B adds payload byte 01); 07 AA 55+4B code-option Set Code Option (0x40C19E); 08/09 AA 55+retap 01/02 Set/Get pair (0x40C22D, 0x40C2C2, 0x40C3D7, 0x40C456); 09 AA 55 (+5B seed) and 0B AA 55 (+9B) CS3 seed writes (0x40C537, 0x40C775, 0x40C8AF); 20..24 AA 55 ISP enter/verify family (0x40C9D5 cmd 0x20, 0x40CAFE 0x21, 0x40CBD5 0x22, 0x40CCBF 0x23, 0x40CD9D 0x24; one function per cmd; 0x40D310 echo-gated re-sends); 25 AA 55+payload (byte 04 at index 4) page write (0x40CE33); 26/27 AA 55 (0x40CF2B, 0x40D03E); 28/29 AA 55+retap (0x40D0D1+0x40D149, 0x40D24B+0x40D2AE); 2A AA 55+5 zero bytes upload token (0x40D36B). Correction 2026-10-22: an earlier pass read the rows 05 09/0B, 05 20..24, 05 25/26/27, 05 28/29, 05 2A with a leading 05; the send sites verify those bytes that follow the cmd are NOT prefixed — 09/0B, 20..24, 25, 26/27, 28/29, 2A are the actual cmd bytes (e.g. before the 0x40C537 send: 0x40C528 writes [esp+0x10]=9, 0x40C52D AA@+0x11, 0x40C532 55@+0x12). The re-send loop at 0x40C5BA/0x40C61D/0x40C680 progressively raises payload byte 01→02→03 until the echo matches — that is the single re-send mechanism the later rows reuse.

All send/read windows are in analysis/out/io_sites.txt, the sentence per command in analysis/out/set_digest.txt. Flow glue in isp_walk.txt function dumps (0x4039C0 zone wrappers 0x40A550/0x40A510).

No flash-read command (fact)

The AA 55 set programs, erases, verifies and checksums, but never dumps a flash range: the commands above cover version, password, encryption, erase-enable, 64-byte program, checksum, code-option, set/get option, seeds, ISP enter 0x20..0x24, page write 0x25, 0x26/0x27, 0x28/0x29 and token 0x2A. The reads in the flow are echo/status gates and per-page verify re-fetches — none returns bulk flash bytes.

Consequence for phase 6: the updater cannot make a stock backup of the device. The only stock copy is the factory image RCDATA 4000 inside the exe, and this tool cannot prove the device's flash matches it byte-for-byte. A pre-flash plan must say that outright rather than assume "backup first", and should demonstrate a recovery path (and prove the write path with the unmodified image on a second unit) before a modified image is tried.

Want-floor: the "expected echo" gate

0x40D310 is the single all-commands read + compare: the function does one 0x25/whatever read frame, then compares the first 4 bytes of the sink with the caller-supplied (cmd,AA,55,…) want-vector and, on mismatch, re-sends the caller's frame and re-reads — 12 callers hand it (frame, want) pairs. Only when the echo matches does 0x40D310 return '5' (success code) or '1'. The tables at 0x40D42A/0x40D3E0 show the second variant: cmp al, 0xe1 + dec [edi] — a counter/flag-blob sanity check done inside the same function.

Frame sizes 8/10/12/64 bytes are the report formats 1–4 (0x4421/0x4428/0x442F cluster). The 0x409D40-zone verify stack, when compared against the wire order, is the ISP-zone echo: 0x40C360 push 9, readback at 0x40c6f0, 0x40BEA0(9).

Code-option (fact)

0x40C19E sends SET code-option 07 AA 55 + 4 bytes, 0x40C22D fires the confirm 08 AA 55 + 01, 0x40C2C2 feeds the readback to the expect gate for the '01'. The 0x40D149/0x40D2AE retap-01 trailing pair re-runs the whole echo-exchange after 05 28/29 AA 55 — a "final echo" of the option state.

Password & erase-gate frames (fact)

Wire frames

  • Short password frame (0x40B740): 8 bytes 02 AA 55 00 <4-byte dword> — the dword is read once via mov eax,[ecx] from the caller-supplied pointer arg, stored at frame index 4. Caller convention (verified at all 7 call sites, e.g. 0x40251F..0x40252E / 0x403A0C..0x403A19): the flow does mov ecx,[this+0x1c] (the flow-controller object's pw-pointer member), push 2; push ecx; call 0x40B740; add esp,4 — frame buffer is the callee's own local, not a caller buffer. The wire password payload is therefore exactly 4 bytes at *(flowCtl+0x1c), not the full 8-character string.
  • Long password frame (0x40BAC0) (V2, out/isp_pw6.txt): 64-byte frame with buffer = transport object+4; writes [obj+4]=02, [obj+5]=AA, [obj+6]=55, zeros [obj+7..0xd] (frame indices 3–9), then one send of length 0x40. No password bytes are copied by this function — pw travels only in the 8-byte short form; the long form's read gate (fn 0x40BB20, site 0x40BC05) still demands echo[4..7] == [0x5b1d6c], so the device fills the 4-byte value.
  • Callers and failure path: short form from seven flows (0x40252E, 0x402FEE, 0x403A19, 0x405FFD, 0x40678B, 0x408BAB, 0x409D90); long form from 0x407E53 only (fn 0x407CA0's Codeoption Erase Protocol Handshake Error!! check); the 0x40BB80 read-gate from six of the same flows. Erase/Codeoption flows treat these frames as their Protocol Handshake step: failure raises 0x40a550's restart path with a handshake MessageBox and status 0x1d/0xe in [obj+0xc0].

The pw-value gate & global 0x5b1d6c

  • The tool loads the default ISP password from FindResourceW(RT_RCDATA=10, id 0xFA7=4007); the resource is UTF-16LE '12345678' (16 bytes, terminator included). Extraction: analysis/out/rcdata_4007.bin.
  • Read gate behind the short frame (esp accounting re-derived byte-exact, out/isp_pw5.txt U1 + out/isp_pw2.txt P5): the 8-byte HidD_GetFeature echo lands in the same local the send buffer used; then return 2 if the read fails, 4 if echo[0..3] != sent[0..3], and the final compare cmp [0x5b1d6c], echo[4..7] → sete al; add eax,4 → return 5 = pw match, 4 = pw mismatch. So 0x5b1d6c is the tool's stored pw VALUE dword, and the device is expected to echo the matching 4-byte value at index 4. This gate-for-value pattern repeats in 10 more command fns (0x40BB20, 0x40BC40, 0x40BCE0, 0x40BEA0, 0x40BFF0, 0x40C140, 0x40CA90, 0x40CD40, 0x40CFE0, all cmp [0x5b1d6c],[esp+0x18]-shaped).
  • The global 0x5b1d6c: .data initial value is 0xFAFAFAFA — literally the only FAFAFAFA in the whole file, a deliberate poison/'not yet set' marker. All 16 .text references are mov reg,[0x5b1d6c] reads in echo gates; no addressed write, no lea-address-take, no base-pointer constant for the 0x5B1C00..0x5B2200 zone exists anywhere in the image (aligned full-zone sweep out/isp_pw6.txt V3), so the runtime writer is register-indirect (through the controller-object side of the +0x1c pathway or a runtime-computed base). The chain that must eventually supply it: RCDATA 4007 '12345678' (UTF-16LE, out/rcdata_4007.bin) → dialog CString member +0xEC (loader fn 0x427120; only caller 0x427660) → conversion → slot value.
  • Status: wire shape verified; the exact byte semantics of the 4-byte payload (which conversion of the UTF-16 resource lands in the controller pw slot: ascii-'1234' 0x34333231, utf16-'12' 0x00320031, dec 12345678 = 0x00BC614E, or hex 0x12345678) remain open — the exe's SHLWAPI!StrToInt64ExW (STIF_SUPPORT_HEX) sites are candidates but not yet tied to this chain. The 16 read-gates pin one hard fact: tool-side stored pw dword must equal the device's echoed value, so tool and device agree on whichever encoding is chosen.

Chip-name registry (SZK671F) & the I2C verdict (fact)

  • Registry strings: the chip-name table sits at 0x588F98..0x589074: SN34F280, SN32F24xC, SZK671F, SN32F290, SN32F280, SN8F5280, SN8F2267F, SN32F24xB, SN32F26x, SN8F22E8xB, SN32F22x, SN32F23x (‘Not Connected’ heads it at 0x588F7C). SZK671F is one member of that family list, nothing more exotic.
  • Installer sites: five near-identical registration code sites (0x556285, 0x556735, 0x556CD0, 0x557D70, 0x558E50, all in .text tail; disasm analysis/out/isp_open.txt ‘Q3b’ and ‘Q6’) each build a per-protocol-variant copy of the chip list: they write globals in the 0x5BD020/0x5BD16x/0x5BD38x-0x5BD41x zone with config ids 0x12..0x14 and a tag byte pair 0x22..0x25 on the stack slot, pushing each chip name string and ending in a common push <vtable> (0x55A070/0x55AAB0/0x55A140/0x55A2D0/0x55A310) + shared-call pattern. I.e. the tool keeps five protocol variants, each with its own chip-name list; the device gate selects between variants by matching the connected device against these names.
  • EVT/I2C verdict: the exe contains no I2C/EVT machinery (searched: I2C/IIC/Iic/i2c/EVT/evt across every printable ASCII and UTF-16 run of the file). The two ‘C&C=IIC’ hits at 0x56B0FE/0x57EA5E are harvest false-positives from pointer-table bytes (running bytes like 43 00 26 00 ... read as UTF-16); the hex windows around them show code-pointer arrays, not strings. The tool's device surface remains HID-feature-reports only, matching the import map. The status item ‘EVT/I2C unlock’ is closed: no such mechanism exists in this exe.

Finish-floor (fact)

The last wire act before restart: after the 0x28/0x29 pair, the 01 retap echo confirms persisted state; failing it raises 0x40D310's '5' status and the flow ends (single-shot, no outer loop retry — the caller restarts the whole attach).
