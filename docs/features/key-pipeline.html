Key pipeline & remap surface — key id to HID usage in RCDATA 4000

Status: phase-4 code walk verified (sensor front end, position map, usage↔id table, four Fn-overlay tables with the OS mode byte Fn+S/Fn+D/Fn+A → Windows/Mac/Android, sentinel, actuation constants, change filter, scan front end); · Read when: planning a key remap, a rapid-trigger change, or touching analysis/fw_keys.py

What it is

The runtime path from a scanned key to a HID report, as code in 0x0000–0x9810 plus tables in the band. Everything below is byte-verified by analysis/fw_keys.py (report: analysis/out/fw_keys.txt) and by the recursive-descent disassembly in analysis/fw_code.py. Addresses are image offsets, which equal flash addresses because the vector table sits at 0x0.

  • Key ids live in a 0x00–0x78 space (120 values, id 0x6F absent), not in the 0x01–0x3D space used by the layout tables on Keymap & LED tables. The 61 wired keys are a subset; id 0x7D is the "no key" sentinel.
  • Four layer tables turn a pressed usage into an output usage or an extended action code; this is the remap surface.
  • Actuation and change filtering are separate from the mapping: per-key u16 value/threshold compare, then a hold-timer filter.

Sensor front end (fact)

Byte-verified by analysis/fw_sensor.py (analysis/out/fw_sensor.txt). The scan runs in the IRQ handler at 0x0FC8 (vector 33), not a polled loop.

  • Analog block 0x40027000. Sixteen 32-bit channel results at +0x00…+0x3C, status/start at +0x10C (bit 0 = ready, write 3 to start), control at +0x100 (bit 0x10 re-arms).
  • Channel order is not offset order. The fill at 0x1028–0x1070 reads channel→result c0=+0x24, c1=+0x20, c2=+0x3C, c3=+0x38, c4=+0x1C, c5=+0x18, c6=+0x14, c7=+0x10, c8=+0x0C, c9=+0x08, c10=+0x04, c11=+0x00, c12=+0x34, c13=+0x30, c14=+0x2C, c15=+0x28 (asserted by the probe).
  • Raw matrix 0x2000221E: 8 channels × 16 drive lines of u16, row stride 0x20; the row index is *(u8*)0x20000326. Only low 16 bits of each result are kept. Drive-line select is 0x6CDC(row), which strobes GPIO banks 0x40037000/0x4003A000 after 0x588C sets the analog pins.
  • Position → logical id. 0x56E4(row, col) computes id = row + 8*col (0x56E8), reads the raw u16, then maps the position through the 128-byte table at 0x16A96: 0x7D = unpopulated, otherwise the logical key id used by everything downstream. 61 of 128 positions are populated (probe asserts 61 distinct ids); all resolve in the usage table.
  • Sample conditioning. raw < 0x3E8 (1000) is clamped to 0x3E8 (0x5708); otherwise the raw value is floated and fed to a per-key adaptive filter 0x73A8 with a 24-byte record at 0x20001330 + id*24 (init by 0x7E74: [0]=[+0x10]=1e-05, [+0x14]=0.01, +4/+8/+0xC=0). The filter output becomes the u16 written to 0x20000100 and handed to 0x32AC.
  • Downstream writes. 0x32AC stores the sample as value[id] @ 0x2000376E (0x3412), seeds 0x2000366E[id] on the first sample (0x3416), and keeps a running maximum in 0x200030AE (0x3336) — so 0x30AE is the tracked rest/peak value, not the per-key threshold word.

  • Entry into the per-key state machine is 0x32AC; its only static caller is the tail-call b.w 0x32AC at 0x5738, which is the end of the sample→u16 conversion (vcvt.u32.f32 of a float distance, then strh into a per-key field).
  • 0x32AC starts with the current id in 0x2000008B, splits it into byte/pin (id>>3 at 0x200000F1, id&7 at 0x200000F0) and bails to the "no key" path on cmp r7,#0x7D.

usage ↔ id table (fact)

  • At 0x16DD8: a sentinel entry (0x7D, 0x00) followed by 120 two-byte entries, byte 0 = id, byte 1 = HID usage. The u16 at 0x16EC8 is the count, 120.
  • Ids run 0x00–0x6E then 0x70–0x78 (0x6F absent). Unassigned usage 0x00 sits at ids 0x0D–0x0F, 0x60, 0x71–0x72, 0x77, 0x78.
  • Anchors: 0x00→0x29 Esc, 0x01–0x0C→0x3A–0x45 F1–F12, 0x10→0x35 backtick, 0x11–0x1A→0x1E–0x27 1–0, 0x1B/0x1C→0x2D/0x2E, 0x1D→0x53 NumLock, 0x20→0x2B Tab, 0x4C→0x28 Enter, 0x53→0x2C Space.
  • 0x327C searches in the reverse direction (usage → id): walk byte 1, return byte 0, fall back to 0. Callers at 0x7630, 0x763C, 0x10988, 0x128B6.
  • The 61 wired positions map to ids 0x00, 0x11–0x1C, 0x20–0x2C, 0x30–0x3C, 0x40–0x4C, 0x50–0x57, 0x5C (see the position map above); the 0x01–0x3D ids of the layout/LED tables are a separate space.

Layer tables — the remap surface (fact)

Addressing and lookup

  • Four tables of 51 rows, 2 bytes each, stride 0x66: 0x16C3E, 0x16CA6, 0x16D0C, 0x16D72. Layer 3 ends exactly where the usage table begins (0x16DD8).
  • Row = (byte0, byte1). Only layer 0's byte0 is the input usage; 0x7378 searches layer 0 for byte0 == pressed usage and returns the row index, bounded by the u16 0x16CA4 == 51.
  • The active layer comes from the OS mode byte 0x20000088+0x26 (0x200000AE, values 0–3). The four bases are loaded once at 0x2FF6–0x2FFF; the output is byte1 of the same row, fetched at 0x302A/0x3034/0x303E/0x3048 and stored into [obj+4].

Per-OS overlays, not a base map

  • Layer 0 is the Windows Fn map: 1–0 → F1–F10, -/= → F11/F12, K→Home(0x4A), L→End(0x4D), U→PrintScreen(0x46), I→ScrollLock(0x47), O→Pause(0x48), Delete→Insert(0x49), ;→PgUp(0x4B), '→PgDn(0x4E), /→Insert.
  • Layers 1–3 share every output byte with each other (all 51 rows). They differ from layer 0 only in rows 1–12 (F1–F12) and 14 (Fn): layer 0 emits Windows media/brightness codes there, the others pass the usage through (row 14: 0xD1 vs 0xE3).
  • The mode byte's writers decode the same extended codes the overlay produces: row 44 A→0x9C, row 45 S→0xAB, row 46 D→0xAC, and 0x2B5E writes mode 0 on 0xAB (Fn+S), 0x2B3C mode 1 on 0xAC (Fn+D), 0x2B80 mode 3 on 0x9C (Fn+A). Nothing writes mode 2, so layer 2 is a third copy of the Mac column that no path can select. The AULA MINI60 HE MAX manual pairs Fn+S/Fn+D/Fn+A with Windows/Mac/Android, which names layer 0 = Windows, 1 = Mac, 3 = Android.
  • The chain is live: 0x1456E calls the dispatcher 0x2FF0 and 0x1457A then calls the mode setter 0x2AE4 (also called from 0x887A); 0x2AE4 re-reads [obj+4] and branches on 0xAB/0xAC/0x9C at 0x2B26–0x2B32.

Output space

  • Outputs ≥ 0x9B that are not HID usages are extended action codes consumed by the report builder around 0x2B00: 0x9B, 0x9C, 0xA0–0xA3, 0xAB, 0xAC, 0xB0, 0xB1, 0xB3, 0xB5, 0xB9, 0xBA, 0xBF, 0xC1, 0xD0–0xD7, 0xDA, 0xDF, 0xEB, 0xFE.

Actuation and change filter (fact)

0x5498   r0 = new u16 sample, id = *(u8*)0x2000008B
         prev = state[id]                    ; u16[128] @ 0x20003A16
         if prev == 0:      state[id] = r0; timer[id] = 0x1388; return 1
         if prev == r0:     timer[id] = 0x1388; return 0        ; stable
         if |r0 - prev| >= 0xA: state[id] = 0; return 1          ; jump
         if --timer[id] == 0:   state[id] = 0; return 1
         return 0
  • 0x1388 = 5000 is the hold/reload value (0x54A6), 0xA the minimum delta (0x54DE), both inside 0x5498; its only caller is 0x35B2, inside the per-key loop.
  • Actuation constants in 0x32AC: press/release u16 0x960 (2400) and 0x640 (1600) written to the per-id arrays at 0x33D0/0x33D8, with 0x8400 passed to the 0x55C4 helper at 0x33E0.
  • The compare at 0x3758 reads value[id*2] @ 0x2000376E against threshold[id*2] @ 0x200030AE minus the 0xC hysteresis gap (0x3764).
  • Per-id u16 flags at 0x200031AE carry the actuation state in bit 15 (and 0x8000 / orr at 0x3348); per-id 8-byte settings records are read at 0x200028AE.

What a remap would touch (fact + plan)

  • To change what a key sends, rewrite byte 1 of the row whose layer-0 byte 0 is that key's usage, in the layer(s) that should change — one of layers 0/1/3 for a single OS, or all three for every OS. Layer 2 is unreachable and needs no edit. Row order is fixed, so a remap is a table edit, no code change.
  • To change which usage a physical position produces, edit the 0x16DD8 table (id → usage); keeping it a function keeps the reverse lookup at 0x327C consistent.
  • Nothing in the image writes these tables: the only references are the readers above (0x030E8–0x030F4 for the layers, 0x032A4/0x032A8 for the usage table), and there is no store to them. Per-profile remaps must arrive as patched flash or through a settings copy elsewhere (open).
  • Actuation and rapid-trigger behaviour are code constants (0x960/0x640/0xC/0xA/0x1388) — changing them is a code patch, not a table edit.

Open

  • Sensor front end written up, two loose ends. The chain is verified (section above), but the writer of the scan row index 0x20000326 has no direct literal reference — it is reached through a base computed at runtime — and the 0x6CDC drive-line helper only switches drive lines 0–5. Also note the earlier 0x106B0 candidate is not the matrix scan: it initialises the 0x4001F000 block.
  • Settings area 0xB000–0xBA00. The loader copies 0xB000 + id*4 and 0xB600 + id*8 into RAM, but that whole span is zero in the factory image (recorded as "gap2" in the region map) — i.e. an erased parameter page with defaults supplied elsewhere, not padding.
  • Layers 1–3 byte 0 is not the input usage (row 1 is 0xCF,0x3A in layer 1 vs 0x3A,0xC1 in layer 0). Only byte 1 is read, so byte 0 is a stale column: in the 13 F-row/Fn rows it holds values from the same extended-code space (8 of 12 equal layer 0's Windows outputs), and it drives nothing.
  • Assignable-key catalog at 0x9600. 112 four-byte records (kind 2 or 3); kind 2 keeps the usage in byte 2 (02 00 29 00 = Esc), kind 3 in bytes 1–2 (0xE9 volume-up, 0x53 NumLock, 0x0192 at the 03 92 01 00 record). No literal pointer to it exists, but the consumer is this code after all: the per-key loader at 0x5950 reads 0x9600 + id*4 (four bytes, stride 4) into the 4-byte-per-key RAM copy at 0x200024AE, alongside 0x8400→0x200030AE, 0x8500→0x200031AE and the blank settings area 0xB000/0xB600.
