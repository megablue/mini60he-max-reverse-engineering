Modification surface — where a patch goes in RCDATA 4000, and what gates it

Status: phase-5 inventory (data hooks, LED value tables, code constants and the four gates pinned byte-exactly, plus a remap planner that plans byte edits) and the Fn action enum decoded to a built four-byte bake (out/fw_volplus.bin, nothing flashed) · Read when: choosing a modification, planning a specific key remap, computing a patch offset, decoding an Fn output byte, or checking what a byte edit would break

What it is

Every candidate mod — key remap, rapid-trigger tuning, lighting — reduced to an image offset, a unit of edit and the code that reads it. The artifact is analysis/fw_patch.py → analysis/out/fw_patch.txt, regenerated from the pinned image (0x7E000 B, SHA-256 06A1A474…4A88E0); the chip-record size gate is analysis/isp_gate.py → analysis/out/isp_gate.txt. Image offsets equal flash addresses because the vector table sits at 0x0.

  • Three key-remap hooks, all plain table edits: the usage table, the four per-OS Fn overlays, and the physical scan grid.
  • Actuation and debounce are two data tables plus three code immediates — the tables set defaults, the immediates set behaviour.
  • Lighting is reachable as pure value runs (palette, hue ramp, presets); the ramp band is mixed data and must be treated as fragile.
  • Four gates decide whether a patched image is accepted: length, version word, tool-side checksum, signature (last one absent).
  • Nothing here builds or writes an image: phase 6 stays user-gated per the plan.

Key remap — three hooks (fact)

HookOffsetsUnitEffect
Usage ↔ id0x16DD8–0x16ECA2 B per key, edit byte 1the HID usage a logical id sends — the primary remap
Fn overlays0x16C3E, 0x16CA6, 0x16D0C, 0x16D7251 rows × 2 B per layer, edit byte 1the output code Fn+key produces, per OS layer
Scan grid0x16A96–0x16B161 B per physical cellwhich logical id a matrix position reports
  • Usage table. Sentinel (0x7D,0x00) first, then 120 pairs; the u16 count at 0x16EC8 is 120. Read by the usage→id search 0x327C. Leave byte 0 (the id) alone; changing it re-targets an id rather than a key.
  • Fn overlays. Only layer 0 searches byte 0 (the pressed usage, 0x7378); layers 1–3 have byte 1 read directly. Layer 2 has no writer for the mode byte, so editing it changes nothing at runtime.
  • Mode byte writers. 0x200000AE is written in 0x2AE4 itself: 1 at 0x2B3C (Mac), 0 at 0x2B5E (Windows), 3 at 0x2B80 (Android); the trigger codes 0xAC/0xAB/0x9C are compared at 0x2B26/0x2B2A/0x2B2E. Mode 2 is still unreachable.
  • Traps. Duplicate usages are not rejected — two keys then report the same usage. A scan-grid id that no table knows leaves a dead position; the per-key RAM arrays are 128 entries, so ids stay under that.

Worked remap plan — CapsLock sends Esc

analysis/fw_remap.py → analysis/out/fw_remap.txt is the planner: it resolves a request like {"key": "CapsLock", "to": "Esc"} through the current map, validates it, and prints the byte edits. It never writes an image — building one is phase 6.

id 0x30 currently sends 0x39 (CapsLock)
usage byte for id 0x30 sits at  0x16E3B   (0x16DDA + 2*index, index 48)

0x16E33  30 2d 5f 2e 60 2f 61 30 [39] 31 04 32 16 33 07 34   before
0x16E33  30 2d 5f 2e 60 2f 61 30 [29] 31 04 32 16 33 07 34   after
  • One byte. Length, checksum and every other field are untouched; the version word below 0x16A96 keeps its value.
  • Validation the planner reports. The target id must appear in the scan grid (id 0x30 does), the new usage must not be 0x00, and a duplicate is flagged only when the edit creates one — here usage 0x29 already belongs to id 0x00, so the report says "merges onto ids 00, 30": two keys with one function, which is the intent.
  • Swaps are two requests in the same list; the plan is computed from the original table in one pass, so order does not matter.
  • Free rows. Ids 0x0D, 0x0E, 0x0F, 0x60, 0x71, 0x72, 0x78 send usage 0x00; none is physical, so they are spare table rows rather than spare keys.
  • Unverified. Nothing shows the companion app writing a keymap at runtime; if it does, a firmware-side edit could be overridden. That needs a capture, not more static analysis.

Fn actions — the vendor enum (fact)

The Fn output byte is not a HID usage. It is a vendor action code, and 0xB0 + k indexes a u16 table of consumer usages at 0x16BF6. Four members were confirmed on the keyboard; that fixes the offset and makes the rest readable.

enum  table   action        source
B0    B5 00   Next          Fn+F9  verified on keyboard
B1    B6 00   Previous      Fn+F7  verified on keyboard
B2    B7 00   Stop          table
B3    CD 00   Play/Pause    Fn+F8  verified on keyboard
B4    E0 00   Volume        table
B5    E2 00   Mute          Fn+F10 verified on keyboard
B6    E3 00   Bass Boost    table
B7    E4 00   Loudness      table
B8    E5 00   Bass Down     table
B9    E9 00   Volume Up     table
BA    EA 00   Volume Down   table

A dead row to spend

Layer 0 has 51 rows keyed by input usage, and only 13 can never fire on this board: rows 1–12 are keyed on F1..F12 (a 60% has no F-row) and row 32 on 0x4C Insert — no scan position emits that usage. Row 32 maps Insert → Delete, so repurposing it costs nothing:

0x16C7E  4C 49   row 32: Insert -> Delete             before
0x16C7E  4F B9   row 32: Right Arrow -> Volume Up     after
  • No length change, no relocation. Row count at 0x16CA4 stays 51 and every byte below 0x16A96 is untouched, so the version gate and the RCDATA size gate see a factory-shaped image.
  • Volume already ships. Rows 11/12 map F11/F12 to 0xBA/0xB9, so Fn+F11 and Fn+F12 are Volume Down/Up on stock firmware — a free check of the whole chain before any write.
  • Dependency. The Fn lookup reads the usage that reaches [0x2000008C], so Right Arrow has to be the usage the key actually sends. The four-byte bake below makes that true in firmware; see the bake.

Fn + Right Arrow — the four-byte bake

The Fn state is keyed on the usage value 0xAF, not on a key id: on the owner's keyboard the key at the old RAlt position produces Fn+1 = F1 today, only because an app remap put 0xAF on it. The usage table at 0x16DDA is one (id, usage) pair per key, so moving a value between two ids moves the role between two physical keys — and the owner's intended keys are exactly the two that now hold the swapped pair:

0x16C7E  4C -> 4F   Fn map row 32: Insert becomes Right Arrow
0x16C7F  49 -> B9   Fn map row 32: Delete becomes Volume Up
0x16E83  E6 -> AF   id 0x54 (old RAlt) becomes Fn
0x16E85  AF -> 4F   id 0x55 (stock Fn) becomes Right Arrow
  • Net behaviour. Old RAlt key = Fn; old Fn key = Right Arrow; Fn + Right Arrow = Volume Up (0xB9 → consumer 0x00E9). RAlt and the factory Fn position are gone — that is the trade the owner asked for.
  • Independent of the app. Because both usages are in the table, no NVM remap has to be active; re-flashing the whole image would otherwise wipe those pages. Ids keep their scan positions, so per-key actuation records stay on the same physical keys.
  • Still in the gates. Four bytes, no length change, all at or above 0x16A96; the version word below it and the RCDATA size are untouched. analysis/fw_volpatch.py --chord-only builds the two-byte variant for the case where the app remap is guaranteed to stay.

Actuation and debounce (data + code)

  • Default tables. 0x8400 is 112 × u16, all 0x960 (2400); 0x8500 is 112 × u16, all 0x640 (1600). They are copied into the per-key RAM arrays by the loader at 0x58FE–0x5990.
  • Code seeds. 0x33D0 and 0x33D8 write those two literals into the per-key arrays when the NVM page is blank; 0x33E0 loads 0x8400 as a table base.
  • Catalog. 0x9600, 112 records × 4 B: 102 kind-2 (usage in bytes 2–3) and 10 kind-3 (firmware function in bytes 1–2; first at record #13, 03 e9 00 00 = volume up).
  • NVM page. 0xB000 + id*4 and 0xB600 + id*8 are blank in the factory image, so defaults are synthesized in code. Editing them sets defaults, but a settings save from the companion app overwrites them.

Behaviour constants are instructions, not tables — copied exactly so a patcher can find them:

0x3764  a1f10c0c  sub.w  ip, r1, #0xc    ; hysteresis, 12 counts (cmp at 0x3768)
0x54DE  0a2e      cmp    r6, #0xa        ; commit at |delta| >= 10
0x54A6  41f28836  movw   r6, #0x1388     ; hold timer, 5000
0x54BC  24f81160  strh.w r6, [r4, r1, lsl #1]   ; timer reload on no change

Correction recorded here: earlier notes called 0x33D0/0x33D8/0x33E0 "threshold compares". The bytes are two strh seeds and one table-base add — they initialize, they do not decide.

Lighting — value tables

  • 0x17668 — palette triplets: ff0000 ff8000 ffff00.
  • 0x17837 — RGB hue ramp, ff0000, ff0100, ff0200, … ffff00 (553 B).
  • 0x17A83 — preset runs: c8 96 64 4b 19 19 then c8 96 64 4b 28 28 (200/150/100/75/25).
  • 0x170B9–0x17354 — ramp/fade tables (arithmetic byte ramps; mixed with literals).
  • 0x16FF6 — 12 W-pair bytes; 0x17E38–0x17F00 — per-profile hues with 01 1d headers.
  • 0x174B9 — 16-byte cell records; semantics still open, do not edit blind.

Safe first targets are the palette, the hue ramp and the preset run: pure value runs with no code pointers. A wrong edit inside 0x170B9–0x17354 breaks the ramp engine rather than merely recolouring.

Gates a patch must survive

  • Length. The RCDATA size gate (0x4272BD) compares the loaded size against 0x8400 for chip records whose field 0 is zero; records 9–11 have field 0 = 1 and skip the check. Patching in place keeps the length, so the verdict is identical to the stock flow — only growing the image can add a new failure.
  • Version word. The upload flow (0x40144C–0x401486) compares one image dword against the device's four version bytes; the index comes from the chip record (+0x1F → +0xD). Keep the head of the image — everything below the first table at 0x16A96 — byte-identical.
  • Tool-side checksum. No checksum field lives in the image; the tool recomputes (0x40A800 big-endian 16-bit word sum, 0x40A7D0 32-bit byte sum) from the file it loaded, so a patched image is self-consistent and the displayed value changes.
  • Signature. The Authenticode signature covers the exe, not RCDATA 4000, and no signature check appears in the upload path. The real failure mode is an interrupted write, with the bootloader outside the 0x7E000 span.

Not established

  • Which image dword the version gate reads for this chip (the index is a record field; the offset follows from it).
  • The 0xB000/0xB600 NVM record layout, and whether an in-image default survives the first settings save.
  • Cell-record semantics at 0x174B9.
  • Whether pages are encrypted before write — the Set Encryption Algorithm command exists; its default state is unknown.
  • Everything is static: no modification has been built, flashed or observed on hardware.
