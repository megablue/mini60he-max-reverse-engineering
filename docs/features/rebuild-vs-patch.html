Rebuild or patch — why reconstruction is out and how far patching reaches

Status: decision (2026-10-22) — the image is patch-only; patching has three levels and roughly 400 KiB of blank flash for hooks · Read when: asking whether the firmware can be rebuilt from source, scoping a feature that has no table slot, or justifying a hook into free flash

The question and the verdict

Can the firmware be rebuilt from the ground up, from source? No — not from the evidence in this repository. Both readings of the question are closed:

  • Decompile, then recompile byte-exact. Impossible even with perfect decompilation. The image is vendor Thumb built by an unknown SDK, toolchain and link order, and no symbol table survives; a recompile would differ in every non-trivial function. "Byte-identical" is not a data problem, it is unattainable in principle without the original build.
  • Write new firmware that behaves the same. Not blocked by the binary but by hardware knowledge — see the gap list. Without the SoC register map, debug access and the second radio, a rewrite would be a new wired keyboard, not this one.

What the evidence does support: byte edits in known tables, and new code placed in unused flash. That is the patch spectrum, and it is the project's decision.

Why a rebuild is out

On the device side

  • The SoC is undocumented here. The notes know which registers are touched — USB 0x4001F0xx, LED 0x4001B2xx, Hall 0x40027000, GPIO 0x4003{7,8,9,A}000, clock 0x4002103C, flash 0x40057000 — but not their semantics: clock tree, USB PHY and endpoint setup, flash timing, sleep. The names SN34F280/SN8F2250 exist only as strings in the updater.
  • No debug access identified. No SWD or JTAG path is documented, and the updater has no flash-read command, so there is no way to dump the current flash, single-step or instrument a candidate build. This is the difference between an RE project and a firmware-development project.
  • The bootloader is unknown. Only the PC-side ISP protocol is mapped; the device-side entry handshake, bootloader-ID check, page-program mechanics and therefore the recovery path for a bad image are unverified. A from-scratch app would still have to be a valid payload for that bootloader.

Around the device

  • The runtime config protocol is unexamined. The updater was reversed; the app that writes remaps and macros talks to the keyboard over HID feature reports at runtime, and that protocol — plus the exact NVM format it writes — is inferred from the firmware's read sites, never observed from the writer.
  • Wireless is a second computer. The RF/BT module's firmware is not in this image, its transport is not identified (no UART, SPI or I2C controller appears in the peripheral set, yet Fn+W commands Bluetooth host 2), and the dongle is separate again. Any rewrite without PCB work ships a wired-only keyboard.
  • No build system. No linker script, scatter file, toolchain identity or linker order; the vector table is the only layout evidence.

The patch spectrum

"Patch the binary" is not one technique. Three levels, in ascending risk:

LevelWhat changesExamples
1 — table or constanta value at a known offset in a known tablekeymap usage, Fn overlay row, LED palette, hysteresis constant
2 — in-place codeone or two instructions in a verified windowchange a compare constant, force a branch
3 — hook into free flasha bl at a function entry plus new Thumb at 0x20000+tap-hold, combos, real multi-step macros, new Fn actions

Why level 3 is reachable. The app span is 0x7E000 but only about 0x18600 is used. The rest is 0x00 fill except two islands: the 0xAE10–0xAFFF code chunk and the 0xB000–0xBA00 NVM parameter page. That leaves roughly 400 KiB of blank, programmable space. A level-3 build needs no vendor SDK: arm-none-eabi-as, a linker script placing .text at 0x20000, objcopy -O binary, then a splice — with a verifier asserting the diff is exactly the intended offsets, the pattern already used by analysis/fw_volpatch.py and analysis/mkflasher.py.

What constrains every flash

  • No readback, no breakpoints. A patch must be provably correct by construction: disassemble the exact window, prove register and stack state are unchanged, and keep the change small enough to review by eye.
  • Every flash is a whole-image write. The blank 0xB000/0xB600 pages overwrite user settings, so app-side remaps and macros are re-entered after each write (confirmed on hardware, 2026-10-22).
  • Interrupted write is the brick scenario. The bootloader sits outside the 0x7E000 app span, but recovery is unverified.
  • Wireless behaviour is out of reach. The dead window after wake lives in the RF module; nothing in this image fixes it.
  • Length preservation keeps the gates satisfied. The tool recomputes the checksum itself, the RCDATA size gate only trips on growth, and the version compare is a pre-write refusal rather than a brick risk. All bakes so far sit at ≥ 0x972E; the gate's version dword is somewhere in the low image, so nothing below 0x16A96 moves without a hardware-proven reason.

The rule that follows

  • Table first. Anything expressible as a table row or a constant stays level 1 or 2. Highest confidence, smallest blast radius, and every byte provable against the pinned image.
  • Level 3 only for features with no table slot — and only after a level-1 or level-2 patch in the same mechanism has been validated on hardware (the row-32 bake was proven that way, without a second flash).
  • One falsifiable hypothesis per write. Prefer zero-flash validation where a stock behaviour already exercises the path — Fn+F12 = Volume Up proved the 0xB9 enum without writing anything.

Not established

  • Whether SWD/JTAG pads exist on the PCB, and whether the bootloader can be re-entered after a failed app image.
  • The exact dword the version gate reads, and whether it tolerates edits in the low image beyond the ranges already exercised.
  • The wireless module's transport and firmware — needs PCB identification.
  • Level 3 itself: no hook has been built or flashed yet. The reasoning above is about feasibility, not a proven result.
