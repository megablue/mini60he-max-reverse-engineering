Tap and hold — arrow on tap, modifier on hold (feasibility, RCDATA 4000)

Status: feasibility study (2026-10-24, static) — no table can express it, so this is the smallest code patch on the roadmap (~300 B, 4 keys, 32 B RAM); the millisecond tick, the per-key press/release state and the modifier latch are verified, the exact interception line and the release edge are not · Read when: asking for tap-and-hold keys on the right-hand cluster, planning the first patch that adds code, or deciding whether the arrow remaps are worth their cost

What it is

The request: the four keys at the lower right should send an arrow when tapped and their normal modifier while held — right-Shift taps Up, the Menu key taps Left, right-Ctrl taps Down, right-Alt taps Right, and each holds its stock modifier.

Verdict: possible, and this is the cheapest new-code patch found so far — smaller than the second-Fn design, with no new peripheral and no host software. It is still level 3: a table-only build cannot do it, because every table in the image maps a key to one value, chosen from the event, never from its duration.

It also removes the compromise baked into the flashed remap: that build bought arrows by giving up right-Alt (it became Fn), right-Shift, Menu and right-Ctrl. With tap and hold the same keys keep their stock roles and gain an arrow on tap, so no key has to disappear.

Why a table cannot do it

  • The catalog (0x9600 + id*4, kind 2 + usage at +2) is one usage per key. The app's per-key record in NVM (0xB000/0xB600) is the same shape: kind 3 is a single special action, not a sequence.
  • The Fn overlay (0x16C3E + row*2) is also one output per row, and it is selected by the Fn flag and the OS mode byte, not by how long a key was held.
  • Nothing stores a press time. The key state machine keeps a value, a peak, an actuation bit and a debounce timer per key; there is no "pending" slot and no duration comparison anywhere in the image.
  • The macro player can wait (its steps carry delays), which proves the machine can time output — but it plays a stored script, not a per-key decision. It is the wrong tool and it lives in RAM, not on the key.

So the patch must add code. That is why this page is a design and not a builder entry in the backlog.

Two designs, one of them unusable

Retro-tap (rejected)

Send the arrow on press and the modifier afterwards when the key is still down. This is what several commercial firmwares do and it is annoying: every attempt at Alt+click first types an arrow, and a held key repeats the arrow until the commit. It also cannot be undone — the host already saw the keystroke.

Deferred commit (the design)

Suppress the press, decide on release. The cost is that the held modifier only appears after the term, which is exactly why the term must be felt as a tap threshold (~200 ms) and why any other key going down must commit immediately — so Alt+Tab typed quickly still carries Alt from its first report.

The state machine

on press of a configured id:
    if Fn flag set, or another key is already down, or slot busy:
        emit the stock usage          # never delay a rollover or an Fn chord
    else:
        pending[id] = {t0 = now, tap, hold}
        emit nothing

every tick, for each pending slot:
    if now - t0 >= TERM:
        emit hold usage (press)
        committed[id] = true

on release of that id:
    if committed[id]: emit hold usage (release)
    else:             emit tap usage, then its release
    clear the slot
  • Term 200 ms for the arrows, one constant; 500 ms during the first bench run so the delay is obvious.
  • Slots four pending records (id, t0, tap usage, hold usage, flags) in blank RAM; the id is already unique per key.
  • Fail-open: a release without a slot, or a slot whose key is already released at commit time, emits the stock usage — a stuck modifier is the one failure mode that must not happen.
  • Bypass: when the Fn flag is set the key keeps its Fn-layer behaviour (so Fn+arrow still recurses through the overlay, not around it).
  • Tap emission is a press report and a release report; the host needs to see both, so they must not be merged into one report.

Open and load-bearing: where the release event reaches the dispatcher, and whether the state machine's actuation bit clears before or after the dispatcher runs. Both decide whether the patch is one branch or two, and the first flash should answer it without guessing.

This build starts from the stock catalog: right Alt returns to 0xE6, Fn stays 0xAF on its own key, and the previous bake's four modifier remaps are unnecessary. The Fn overlay row already proven on hardware (0x16C7E 4C 49 → 4F B9, Right Arrow → Volume Up) is kept, so Fn+Right still works — now genuinely as a chord with the Fn key.

Cost, risk and gates

  • Code: roughly 250–350 bytes of Thumb in blank flash (0x18600–0x7DFFC, avoiding 0xAE10–0xAFFF and 0xB000–0xBA00), entered by one bl from an existing site; plus about 32 bytes of RAM.
  • Flash cycles: 2–3 to land and tune it. Every write erases the NVM settings pages, so app-side remaps must be re-entered after each one.
  • Gates unchanged: length preserved, edits above the version words, checksum recomputed tool-side, signature stale on a patched updater. No readback exists, so every test is a flash.
  • Not addressed: the wireless dead window (RF link establishment, outside this image) and the fact that a held modifier arrives one term late.
  • Failure budget: the state machine can only mis-time a modifier, never wedge one — every path that loses a slot emits the stock usage. That is the property to test first.

Test ladder

  1. No-op hook: branch into new code that immediately returns the stock usage. Proves the bl, the placement and the flash without changing behaviour.
  2. One key, long term: right Ctrl only, 500 ms. Confirms the tick unit, the release edge and the tap emission.
  3. Four keys, 200 ms: the full table; confirms slot bookkeeping and rollover commit.
  4. Add Fn+Right: restore the proven overlay row and check the chord against the tap/hold keys.

Each rung is one visible behaviour, so a failed write is diagnosable from the keyboard alone — no debugger, no readback.

Not established

  • The exact interception line (state machine vs dispatcher) and where the release edge arrives.
  • The tick's step byte value in the running device, so "200 ms" is a term in ticks until measured.
  • Whether a tap's press and release need two report intervals or one; the report assembler is not fully mapped.
  • The Mac mode rewrite at 0x145C6 swaps modifier usages, so a tap/hold key must be classified after it, not before.
  • Nothing here has been built or flashed; all addresses are read from the stock image.
